# 01 概念模型：从七个要点到双环控制

## 1. 问题本质

Agent 工程的根本矛盾，是**执行的不确定性**与**交付的确定性**之间的张力：

- agent 能力强但方差大：同一任务两次执行，路径与质量可能差异很大；
- 上下文有限且易失：对话一断，状态就断，隐含约定随之消失；
- 经验不自动积累：换一个 agent 接手，往往从零开始，重复踩坑。

工作流的任务不是"让 agent 更聪明"，而是**让不确定的执行被结构约束成可预期的交付**。因此它首先是一个控制问题，其次才是一个协作问题。

## 2. 控制论视角

把工程看作一个控制系统：

| 控制论要素 | 在本工作流中的对应物 |
| --- | --- |
| 设定值 | 目标契约（可判定的成功条件，而非口号） |
| 被控对象 | 工程产出（工件、代码、文档、决策） |
| 传感器 | 逐条验收（带证据的判定） |
| 控制器 | 方案与派发（做什么、给谁做、给什么上下文） |
| 执行器 | 子代理（执行者） |
| 状态存储 | 分级记忆 |
| 扰动 | 需求变化、环境变化、agent 失误、上下文丢失 |
| 误差 | 验收偏差与目标偏差 |

这个视角给出四条直接推论：

1. **没有传感器的控制系统是开环的**——"做完"不等于"做对"，整体感觉良好不能替代逐条证据。
2. **没有状态存储的控制系统无法应对中断**——每次重启都从零开始，长任务必然失败。
3. **没有误差分析的控制系统不会进化**——同类错误重复发生，经验停留在个人记忆里。
4. **设定值不可测量时，整个回路失效**——目标不可判定是最致命的漏洞，后面的验收、沉淀、技能化都建立在流沙上。

## 3. 七个要点的重新定位

七个要点不是七个并列的最佳实践，而是**同一个回路上不同功能的着力点**：

| 要点 | 控制论功能 | 回路位置 | 缺失后的典型症状 |
| --- | --- | --- | --- |
| 1 目标讨论 | 生成设定值 | 回路入口 | 方向错误；验收无依据；返工 |
| 2 方案与任务清单 | 控制策略 | 设定值 → 执行器 | 执行碎片化；任务之间无法拼回目标 |
| 3 派发子代理执行 | 驱动执行器 | 回路中段 | 目标停在纸面；主控成为瓶颈 |
| 4 逐条验收 | 传感器 | 回路出口 | 完成度不可信；缺陷后移 |
| 5 错误集收与沉淀 | 误差分析 | 反馈支路 | 同类错误反复出现；经验不可继承 |
| 6 高频动作技能化 | 控制器参数固化 | 反馈支路 | 重复推理；成本高；输出方差大 |
| 7 分级记忆 | 状态存储 | 全局 | 中断即失忆；新 agent 无法接手 |

关键结论：**七者必须闭环才有意义**。只做 1–4 是"有纪律的项目管理"；只做 5–7 是"没有实践来源的知识管理"；只有 1–7 串联，才构成"会进化的工程控制"。

## 4. 三层结构

- **控制层（G/P/D/A/C）**：一次工程的时间线。负责把目标变成可验收的产出。
- **知识层（M）**：跨时间、跨任务、跨项目的状态。负责让下一次不必从零开始。
- **进化层（E/S）**：把控制层的偏差转化为知识层资产的加工过程。

三者的关系是：**控制层产生偏差 → 进化层提炼 → 知识层存储 → 反哺控制层**。缺任何一层，系统要么不可控，要么不积累，要么积累了但用不上。

## 5. 双环结构

```
                    ┌──────────────── 进化环 ────────────────┐
                    │                                        │
  G 目标讨论 ──→ P 方案/任务 ──→ D 派发执行 ──→ A 逐条验收 ──→ C 收敛判定
      ↑              ↑                │              │
      │              │                └── 偏差/失败 ──→ E 错误集收
      │              │                                     │
      │              └──────── 规则/检查项 ←── S 技能化 ←──┘
      │                                                    │
      └───────────────────── M 分级记忆 ←─────────────────┘

  恢复环（贯穿全部节点）：任意节点中断 → 读取工作区状态 → 重建上下文 → 继续
```

- **主干环**：G→P→D→A→C，一次工程的完整时间线。
- **进化环**：E→S→M，由 D/A/C 中的偏差触发，产出规则、技能与记忆，反哺 G/P/D。
- **恢复环**：不是阶段，而是贯穿所有阶段的能力；它依赖工作区里持续维护的状态与工件。

## 6. 核心概念定义

以下定义是后续所有文档的共同语言。

**目标契约（Goal Contract）**
目的（为什么做）、成功判据（可观察）、非目标（明确不做什么）、边界与约束、授权与责任、验收方式、时间盒、失败预案。目标契约是验收的唯一上位依据。

**方案（Plan）**
从目标到任务结构的映射：技术路线、任务分解、依赖关系、风险与对策、里程碑。方案本身也要被验收（见"方案门"）。

**任务卡（Task Card）**
自包含的执行单元：任务 ID、目标、输入（工件指针）、输出（工件契约）、验收标准、依赖、约束、风险、预算、执行者、状态。任务卡的核心要求是**离开对话也能被理解**。

**上下文包（Context Pack）**
任务卡 + 相关记忆切片 + 约束 + 已知坑 + 相关判例。原则是**指针优先于拷贝**：能引用工作区里的工件，就不要把内容复制进上下文。

**验收单（Acceptance Sheet）**
逐条对照验收标准：条目、证据（产物位置、检查结果、差异）、判定（通过/有条件通过/退回/无法判定）、理由、偏差记录。验收单是"完成"的唯一凭证。

**合规验收 / 价值验收**
合规验收逐条对照契约，回答"是否符合约定"；价值验收由目标所有者或人类确认"是否适合目的"。前者可以自动化，后者不能由执行方自证；把前者当终点，是"自动化错觉"的典型来源。

**收敛（Convergence）**
目标契约逐条闭环 + 价值确认 + 遗留风险被显式接受 + 记忆写回完成。**验收通过 ≠ 收敛**：每一项都通过，仍可能整体偏离目标；收敛是站在目标高度的最终判定。

**错误条目（Error Entry）**
现象、根因、影响面、修复、教训、适用范围、置信度、关联任务。错误条目不是日志，是**可被后续工程消费的知识原料**。

**教训（Lesson）**
从错误中抽象出的可复用判断，必须带**适用条件**和**反例**。没有适用条件的教训是教条；没有反例的教训无法被证伪。

**技能卡（Skill Card）**
触发条件、输入、步骤、检查点、失败模式、度量、版本、失效条件。技能是"程序性知识"，与"陈述性知识"（记忆条目）区分。

**记忆条目（Memory Entry）**
来源、时间、置信度、适用范围、反例、复审日期、所有者。没有来源与置信度的记忆，等于谣言。

## 7. 三个基本假说

整套工作流建立在三个假说上。它们不成立时，工作流必须换形态，而不是硬套。

**H1 可判定性**：目标能被翻译成可观察的验收判据。
不成立时（探索型、创意型、目标本身在演化）→ 切换为**探索型工作流**：验收对象从"交付物"改为"问题定义的清晰度、选项评估的充分性、下一步决策的依据"；人类门禁前置。即使成立，也应采用**判据分层**：稳定层（价值、约束、非目标、不可接受后果）必须前置，演化层（本轮验收断言）可以随证据重写但必须留痕。

**H2 可分解性**：目标能分解为可独立验收的任务，且任务之和不偏离目标。
不成立时（强耦合、整体性质量）→ 放弃细粒度任务卡，改用**里程碑 + 整体验收 + 阶段性红队评审**；接受较粗的控制粒度。

**H3 可复用性**：经验能跨任务/项目复用，且复用收益大于维护成本。
不成立时（一次性、高度特化）→ 记忆只做项目级，不做元知识晋升；技能只做局部固化，不建技能库。

这三个假说同时定义了工作流的**适用边界**（详见 06）。

## 8. 相对原构想的补充

原构想覆盖了主干，但有几处概念缺口，需要显式补上：

1. **收敛判定**：原构想把"验收"当作终点，但逐条验收通过不等于目标达成。需要独立的收敛门。
2. **目标变更控制**：执行中目标漂移是常态，原构想没有"目标改了怎么办"的机制。
3. **冲突仲裁**：多 agent 结论冲突、验收争议、记忆冲突时，谁裁决、依据什么、如何留痕。
4. **生命周期与退役**：项目结束、技能过时、记忆失效之后怎么办；只增不减的系统必然腐化。
5. **人类门禁**：目标确认、验收争议、元知识晋升三处必须有人类介入点，否则责任无法落地。
6. **度量**：没有度量，"进化"只是自我感觉；需要复发率、返工率、接手时间等指标。
7. **责任主体（Owner）**：每个目标、每张任务卡、每条记忆都要有明确的所有者，否则多 agent 协作必然责任稀释。

## 9. 与常见范式的区别

- **与提示词工程**：那里优化的是单次交互；这里控制的是多阶段工程的交付确定性。
- **与多 agent 框架**：框架解决"怎么连"，这里解决"怎么控制、怎么验收、怎么积累"；框架可以替换，控制结构不应随之改变。
- **与敏捷/看板**：借用其可视化与迭代节奏，但验收对象是 agent 产出，且**验收者与执行者的独立性**是新增的核心约束。
- **与知识管理**：记忆不是文档库，而是带置信度、适用范围、晋升与淘汰规则的活体。
