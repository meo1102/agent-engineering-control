# 02 通用工作流：七段主干、两道侧环、三道门禁

## 0. 一页纸总览

| 段 | 名称 | 一句话职责 | 核心产出 | 出口门禁 |
| --- | --- | --- | --- | --- |
| G | 目标讨论 | 把"想做"谈成"可判定" | 目标契约 | 目标门 |
| P | 方案与任务 | 把目标翻译成可执行、可验收的任务结构 | 方案 + 任务卡 | 方案门 |
| D | 派发执行 | 把任务交给合适的执行者并跑完 | 产物 + 执行记录 | 执行完成 |
| A | 逐条验收 | 用证据逐条判定是否达标 | 验收单 | 验收门 |
| C | 收敛判定 | 站在目标高度判定是否真的完成 | 收敛报告 | 收敛门 |
| E | 错误集收 | 把偏差变成可复用知识原料 | 错误台账 | 归因门 |
| S | 技能化 | 把高频稳定动作固化为程序性知识 | 技能卡 | 技能门 |
| M | 分级记忆 | 把知识放到正确的层级并治理 | 记忆条目 | 晋升门 |

主干：G → P → D → A → C。
侧环一（进化）：E → S → M，反哺 G/P/D/A。
侧环二（恢复）：任意节点中断 → 工作区状态 → 重建上下文 → 继续。

## 1. G 目标讨论

**输入**：一个意图、一个问题、一份需求，或上一轮的遗留问题。

**核心动作**：用结构化提问把模糊意图逼成可判定契约。目标讨论至少回答六个问题：

1. **为什么做**：动机与价值；不做会怎样。
2. **成功长什么样**：可观察的成功判据（不是"做好一点"）。
3. **明确不做什么**：非目标清单，防止范围蔓延。
4. **边界与约束**：时间、资源、质量、合规、依赖、不可动的前提。
5. **谁负责、谁授权**：目标所有者；谁有权改目标、谁有权验收。
6. **怎么验收、何时算失败**：验收方式与失败预案。

**输出**：目标契约（目的、成功判据、非目标、边界与约束、授权与责任、验收方式、时间盒、失败预案）。

**目标门（五条判据）**：

- 每条成功判据都可观察、可证伪；
- 非目标明确，且与成功判据不矛盾；
- 授权链清楚：谁改目标、谁验收、争议谁裁决；
- 人类对所有权的确认（人类门禁之一）；
- 失败预案存在：什么情况下止损、如何止损。

**判据质量的两条标准**：

- **可判定**：能给出通过/不通过/无法判定三种结论，而不是"感觉还行"；
- **因果贴近度**：判据与目标之间的因果距离足够近——"若不真正达成目标，就很难廉价地满足它"。精确但因果遥远的判据（格式、字数、文件存在）最危险：它让判定变容易，同时让判定失去意义。

**判据分层（兼顾探索）**：

- **稳定层**：价值、约束、非目标、不可接受后果；任何阶段不得违背，必须先定。
- **演化层**：本轮验收断言；允许在证据出现后重写，但必须留痕，并写下"原判据错在哪"作为错误沉淀的输入。

判据分层解决了"判据前置会杀死探索"的问题：前置的是稳定层，演化层可以后到。

**常见失败**：把手段当目标（"上线某系统"而不是"解决某问题"）；成功判据不可判定；非目标缺位导致无限扩张；目标所有者缺位。

## 2. P 方案与任务

**输入**：目标契约。

**核心动作**：

- **方案设计**：技术路线、关键取舍、风险与对策、里程碑。方案不仅要说明"怎么做"，还要说明"怎么证明做对了"。
- **任务分解**：把目标判据映射为任务卡；一张卡对应一个可独立验收的产出。
- **验收标准前置**：验收标准在派发前写定，而不是事后补。
- **依赖与风险**：识别任务间依赖，避免环；标注高风险任务与缓解手段。
- **预算**：每张卡的时间/成本上限，超限即升级而不是硬撑。

**任务卡字段（概念级）**：任务 ID、目标、输入（工件指针）、输出（工件契约）、验收标准、依赖、约束、风险、预算、执行者、状态、所有者。

**方案门（五条判据）**：

- **覆盖性**：目标契约的每条成功判据至少被一张任务卡覆盖；
- **可验收性**：每张卡都有可判定的验收标准；
- **无环依赖**：任务依赖图无环，关键路径清楚；
- **粒度合适**：一张卡应能被一个上下文包装下，且不需要跨会话反复交接；
- **风险有对策**：高风险任务有降级/回退方案。

**两条补充约束**：

- **集成断言**：任务分解必须配至少一条"集成断言"，用于检验"各任务拼起来是否真的达成目标"。逐条验收只能保证局部正确，集成断言负责全局正确。
- **基线钉定**：每张任务卡钉住其验收所依据的目标契约与判据版本；版本变更触发任务状态 `STALE`，而不是让验收悄悄对着旧标准进行。

**常见失败**：任务卡写成"动作清单"而非"交付物"；验收标准写成"质量要好"；分解后任务之和不等于目标（局部最优陷阱）；方案门被跳过，直接开工。

## 3. D 派发执行

**输入**：任务卡 + 上下文包。

**核心动作**：

- **执行者匹配**：按能力、成本、信任度、上下文余量选择执行者；不是所有任务都值得派给最强执行者。
- **上下文打包**：任务卡 + 相关记忆切片 + 约束 + 已知坑 + 相关判例；指针优先于拷贝。
- **完成定义（DoD）**：明确"交什么、交到哪、什么格式、什么算完成"。
- **回报格式**：执行者必须回报：产物位置、自检结果、偏差与未决问题、对验收标准的逐条对应。
- **动作可逆性分级**：删除、对外发布、批量改写等不可逆动作，走更严的门禁与人类确认；可回滚修改可轻量处理。把两者放进同一道门禁，是低频高损事故的常见来源。
- **执行纪律**：产物落盘；状态更新；偏差即时登记，不等验收才发现。

**异常处理**：重试、换执行者、降级范围、升级给所有者；每一种处理都留痕（谁、何时、为什么）。

**常见失败**：上下文包缺关键约束导致返工；执行者自行扩大范围；产物只在对话里、没有落盘；状态不更新导致重复派发。

## 4. A 逐条验收

**输入**：产物 + 验收标准 + 目标契约。

**四条原则**：

1. **逐条**：验收单的条目与验收标准一一对应，不做整体印象打分。
2. **证据**：每条判定必须绑定证据（产物位置、检查结果、差异说明）；无证据即未通过。
3. **独立**：验收者不与被验收者共享同一上下文盲区；高风任务引入"冷眼"评审或红队。
4. **可反驳**：验收结论必须给出理由，允许被申诉与复核。

**验收单结构**：条目 / 验收标准 / 证据 / 判定（通过·有条件通过·退回·无法判定）/ 理由 / 偏差 / 整改项与期限。

**两种状态必须显式存在**：

- **无法判定（UNDECIDABLE）**：证据不足或标准本身有歧义。禁止"不确定时按通过处理"；无法判定必须进入补证、改判据或升级裁决。
- **证迹（Evidence）**：第三方不追问执行者也能观察、可复现的完成依据。"已完成/已测试"是自述，不是证迹。

**两条补充规则**：

- **部分通过（PARTIAL）**：任务完成度是判据集的属性（k/n 条通过），不是任务的属性。缺此状态，逐条验收只剩"全过/全不过"，退化为整体印象。
- **提交即冻结证据**：执行者提交后，证据只能追加、不能改写；否则验收对象会在验收过程中变形，逐条验收失去意义。

**探索旁路**：对无法预先写出判据的任务，允许事后判据，但必须显式标注"事后判据"，并在验收时降低其裁决权重、提高抽样复核比例。把事后判据伪装成前置判据，才是真正的失效。

**合规验收 ≠ 价值验收**：逐条对照契约只能证明"符合约定"；是否"值得要"必须由目标所有者或人类单独确认。把逐条全过当终点，是"自动化错觉"的典型来源。

**验收门（四条判据）**：

- 每条验收标准都有对应的判定与证据；
- 有条件通过的整改项已登记，且有责任人与期限；
- 退回项已明确返工范围；
- 验收者独立性已声明（谁验收、与执行者是否同源）。

**常见失败**：自验自过（同一上下文既做又验）；验收标准在执行中被悄悄放宽；只验"有没有"不验"对不对"；验收争议没有仲裁路径。

## 5. C 收敛判定

**输入**：验收单 + 目标契约 + 遗留问题清单。

**四个条件（同时满足才算收敛）**：

1. **目标闭环**：目标契约的每条成功判据都有对应的验收证据；
2. **价值确认**：目标所有者确认交付物"适合目的"，而不只是"符合契约"；
3. **遗留显式**：未解决的问题、已知缺陷、技术债被登记，并由所有者明确接受（谁接受、为什么接受、何时回看）；
4. **记忆写回**：本轮的决策、判例、坑、状态已写入相应记忆层。

**输出**：收敛报告（目标对照表、遗留清单与接受人、记忆写回清单、下一轮建议）。

**收敛门**：四条全满足；否则不得宣布"完成"，只能宣布"阶段性停止"。

**关键区分**：验收通过 ≠ 收敛。逐项通过仍可能整体偏离目标；收敛是站在目标高度的最终判定。**"完成"应被重新定义为"收敛"，而不是"任务都关了"。**

## 6. E 错误集收

**错误来源**：执行偏差、验收退回、目标变更、协作摩擦、环境异常、判断失误。

**错误分类**（用于归因与统计）：

| 类型 | 典型表现 | 主要责任段 |
| --- | --- | --- |
| 规格错误 | 目标/验收标准本身错了 | G |
| 方案错误 | 路线选错、分解失真 | P |
| 执行错误 | 做错、漏做、超范围 | D |
| 协作错误 | 上下文丢失、交接失真、重复劳动 | D/A |
| 验收错误 | 漏验、误判、标准漂移 | A |
| 环境错误 | 依赖、工具、外部条件变化 | 全段 |
| 判断错误 | 信息充分但判断错了 | 全段 |

**归因方法**：连续追问——现象 → 直接原因 → 根本原因 → 系统性原因 → 可复用教训。区分**点错误**（一次性、局部）与**模式错误**（会复发、有结构性原因）；只有模式错误才值得进入沉淀与技能化。

**归因分层（四层修复方程不同）**：

| 缺陷层 | 判定问题 | 修复方程 |
| --- | --- | --- |
| 目标缺陷 | 目标本身错了吗？ | 重开协商，改目标契约 |
| 判据缺陷 | 验收标准写错/写漏了吗？ | 改判据，回到方案门 |
| 执行缺陷 | 做错、漏做、超范围？ | 重做、换人、补上下文 |
| 约束缺陷 | 预算、依赖、环境不成立？ | 改边界，或止损 |

归因错层是沉淀系统退化为噪声库的首要原因：把判据缺陷归为执行缺陷，同类失败会重复 N 次，且每次都换一个执行者背锅。

**错误台账字段**：编号、现象、根因、影响面、修复、教训、适用范围、置信度、关联任务、状态（开放/已修复/已沉淀/已关闭）。

**去重与合并**：同一根因合并为一条，避免台账爆炸；合并时保留出现次数与不同场景，作为晋升证据。

**归因门**：根因可信（有证据链）、影响面清楚、教训带适用范围、点错误与模式错误已区分。

**回退半径**：错误不仅是记录对象，还必须决定"退到哪一层"。

| 半径 | 回退到 | 典型触发 | 批准者 |
| --- | --- | --- | --- |
| r1 任务内返工 | 同一任务卡 | 单条判据不过 | 执行者/验收者 |
| r2 回方案 | 方案与任务分解 | 系统性不过，或判据不可满足 | 规划者 |
| r3 回目标 | 目标契约 | 目标判据不可判定或自相矛盾 | 目标所有者 |
| r4 跨工程 | 元知识/技能库 | 工程结束后的复盘 | 记忆管理员/人类 |

默认 r1；升级到 r2/r3 需要证据；r3 必须目标所有者批准并计入预算。没有半径定义，系统必然在"目标通胀"（每次失败都重谈目标）与"账本空转"（错误就地消化）之间震荡。

**激励相容**：偏差申报必须有正收益（如降低复核强度），被抓到隐瞒则加倍惩罚；否则理性选择是隐瞒，台账只剩"被抓到的错误"，形成生存者偏差。

**常见失败**：把错误当事故处理完就结束，不沉淀；归因停在"执行者粗心"；台账只增不减；教训没有适用条件，变成教条。

## 7. S 技能化

**什么值得技能化**：

- **高频**：在一定周期内重复出现（阈值可按项目设定，概念上"值得固化的重复"）；
- **稳定**：步骤可复现，输入输出边界清楚；
- **可检查**：有明确的检查点，能判断执行是否正确；
- **有失败模式**：知道哪里容易错、错了怎么补救；
- **收益大于维护成本**：固化后的节省 > 维护与复审成本。

**技能来源**：重复的成功路径；反复踩坑后的规避动作；**元动作**——目标澄清、任务拆解、上下文打包、验收、归因、记忆写入。元动作的技能化收益最高，因为它们跨项目复现。

**技能卡字段**：名称、触发条件、输入、步骤、检查点、失败模式与补救、度量、版本、失效条件、所有者、复审日期。

**技能治理**：

- 技能不是越多越好；技能库膨胀会带来检索成本与误用风险；
- 每个技能必须有**失效条件**与**复审日期**；
- 技能冲突时，以更具体、更新、证据更强的为准，并记录裁决；
- 过时技能退役而非删除，保留历史与退役原因；
- **候选区**：未达样本门槛的技能只进候选区，不进入技能库；候选条目必须带样本量与失效条件；
- **不得从单个错误直接跳级为技能**：错误 → 教训 → 复用验证 → 技能；跳级会丢掉适用条件，使技能变成"在错误场景下正确"的负资产；
- **单一出处**：同一事实不同时以技能和记忆两种形式维护，避免"双账漂移"。

**技能与规则的区别**：规则说"不得做什么"（约束），技能说"如何做"（程序）。二者都从错误沉淀中来，但形态与治理方式不同。

## 8. M 分级记忆

三层结构（详见 04）：

- **L0 元知识**：跨项目稳定的原则、模式、反模式、判断准则；慢变、高证据门槛。
- **L1 项目记忆**：目标契约、关键决策、术语、约束、里程碑、风险台账、错误台账索引、验收判例。
- **L2 区域记忆**：开发记忆、验收记忆、收敛记忆、协作记忆等按区域划分的局部知识。

**写回时机**：目标契约定稿、方案定稿、验收完成、收敛完成、错误归因完成、技能发布。

**写回内容**：决策（为什么这么选）、判例（什么算通过）、坑（怎么避开）、状态（做到哪了）。

**读取时机**：新任务派发、新 agent 接手、目标变更、验收争议、复盘。

**晋升门**：进入更高层级的记忆必须满足证据门槛（跨任务/跨项目复现、反例检验、所有者批准），并带适用范围与复审日期。

## 9. 门禁、角色与人类介入

| 角色 | 职责 | 关键约束 |
| --- | --- | --- |
| 目标所有者（Owner） | 定义并守护目标契约；接受遗留风险 | 对"为什么做"负责 |
| 规划者（Planner） | 方案与任务分解 | 对"怎么做、怎么验收"负责 |
| 执行者（Executor） | 按任务卡执行并回报 | 不自行扩大范围 |
| 验收者（Acceptor） | 逐条验收、出验收单 | 与被验收者保持独立性 |
| 沉淀者（Curator） | 错误归因、教训提炼 | 区分点错误与模式错误 |
| 记忆管理员（Librarian） | 记忆写入、晋升、复审、退役 | 守证据门槛 |
| 仲裁者（Arbiter） | 裁决验收争议与结论冲突 | 裁决必须留痕 |
| 约束持有者（Steward） | 守预算、禁区、不可逆操作边界 | 有权叫停 |
| 对抗者（Red Team） | 专找判据未覆盖却会出问题的地方 | 不负责核对，只负责挑错 |
| 人类权威（Human Authority） | 目标确认、争议终裁、元知识晋升批准 | 不可被 agent 替代 |

角色可以由同一个 agent 兼任，但**必须显式声明**。唯一硬约束：**验收不得由执行者的同一上下文完成**（否则独立性失效，验收退化为自证）。

人类门禁建议设在三处：目标确认、验收争议终裁、L0 元知识晋升。

## 10. 任务状态机

```
draft → ready → dispatched → in_progress → submitted
                                              │
        ┌──────────────┬──────────────┬───────┴──────┐
        ▼              ▼              ▼              ▼
     accepted      conditional      rejected      undecidable
        │              │              │              │
        ▼              ▼              ▼              ▼
    converged    (整改后回到     (返工后回到     (补证 / 改判据 /
                  submitted)      in_progress)    升级裁决)
```

异常状态：`blocked`（等待外部条件）、`cancelled`（目标取消）、`superseded`（被新任务取代）、`stale`（判据/基线变更，需重新绑定）、`undecidable`（证据不足，需补证或裁决）、`partial`（部分通过，k/n 条判据）、`drift`（执行中发现目标/判据不成立，合法上报）。

**责任租约**：每个状态必须绑定"负责下一次转移的角色 + 期限"。没有租约的 `in_progress` 会永远合法，系统无法区分"正在跑"与"已经死了"；超期即视为失联，任务进入可被接手状态。

**工件状态**：`draft` → `candidate` → `accepted` → `superseded` / `archived`。

**铁律**：未验收的产物一律是 `candidate`，不得被下游当作事实引用；`accepted` 必须指向验收单。

## 11. 中断与恢复

**中断类型**：上下文丢失、会话结束、执行者崩溃、人类打断、等待外部输入。

**恢复五步**：

1. 读工作区状态（当前阶段、任务状态、最近更新）；
2. 读任务卡（目标、验收标准、约束）；
3. 读最近验收单与偏差记录（哪些已确认、哪些是候选）；
4. 读未决问题清单（卡在哪、等什么）；
5. 重建上下文包，继续执行。

**恢复的两条原则**：

- **状态与意图分离**：状态回答"到哪了"，意图回答"为什么到这"；两者都要落盘。
- **半成品标记**：中断时未完成的产物明确标为候选，恢复者先判断其可用性，再决定复用或重做。

## 12. 反馈边：谁反哺谁

| 反馈边 | 反馈内容 | 形式 | 批准者 |
| --- | --- | --- | --- |
| E → G | 目标问题清单更新（哪些问题当初没问） | 目标模板修订 | 目标所有者 |
| E → P | 分解检查项、风险清单 | 方案检查表 | 规划者 |
| E → D | 上下文包模板、已知坑 | 派发模板 | 规划者/记忆管理员 |
| E → A | 验收判例、边界案例 | 验收判例库 | 验收者 |
| E → 制度结构 | 新增/修改门禁、判据模板、集成断言 | 结构变更 | 门禁所有者/人类 |
| S → D | 技能调用与检查点 | 技能卡 | 技能所有者 |
| M → G/P/D/A | 相关记忆切片 | 上下文包注入 | 记忆管理员 |

**关键区分**：只有改变"制度结构"的反馈边才是真进化，其余只是积累内容。如果所有回边都只是把信息写进记忆、只影响下一轮上下文，系统没有进化，只是在攒日志。

每条反馈边都要回答三个问题：**反馈什么、以什么形式、谁批准**。没有批准者的反馈边会退化为"建议"，最终无人执行。

## 13. 最小可行版本

如果资源只够做五件事，优先顺序是：

1. **目标契约**（没有它，后面全是空转）；
2. **任务卡带验收标准**（验收标准前置是性价比最高的约束）；
3. **独立验收**（哪怕只做到"换一个上下文验收"）；
4. **错误台账**（哪怕只有一页）；
5. **项目记忆**（哪怕只有一个文件）。

扩展顺序：先加技能化（收益最快），再加 L0 元知识（需要跨项目证据），最后加度量与实验（用于证明进化有效，而不是自我感觉）。
