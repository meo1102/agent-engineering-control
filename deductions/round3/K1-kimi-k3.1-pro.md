# AECW 第三轮独立推演（K1）：完整框架与文档可用性

> 席位：K1　模型：`kimi-k3.1-pro`  
> 审视重点：端到端交付链；目标文档、开发任务文档与项目产物的可用性；五态是否混淆文档、任务、阶段与项目。  
> 材料边界：仅依据 `BRIEF-v3.md`、`REPORT.md`（v0.2）与 `REPORT-v2.md`（v0.3）作概念推演，不讨论技术实现。  
> 证据说明：【确定】表示可由材料原文直接确认，或仅靠概念一致性即可推出的必要区分；【推测】表示本席提出、尚需纸面走查或实践检验的框架判断；【存疑】表示材料不足以决定、必须由人类选择或依赖具体情境的问题。三者都不是统计置信度。

## 0. 一句话总判断

**【推测】本轮构想值得保留，但必须作收缩性重构：把五态严格限定为“某一文档版本对某一消费者、某一用途、某一组判据的可用性判定”，把任务执行、阶段验收、项目可用性和最终完成留在各自维度，并把“真实使用”解释为对目标情境和实际结果的检验而非在工作区里观看演示；否则，这条更完整的交付链只会更高效地制造“文档全通过、任务全完成、项目不可用”的合法假象。**

这一判断不是给原构想补几个术语，而是改变其控制对象：交付链传递的不是“完成”，而是**有限授权**；验收链确认的不是“上游都说自己做好了”，而是**当前产物在明确边界内是否值得被依赖**；进化链产生的也不是“原项目更进一步”，而是**需要另行验证的新候选行为**。

## 1. 相对 v0.2/v0.3 的继承、冲突与修正

### 1.1 必须继承的遗产

【确定】v0.2 的判据信任根、程序性独立、组合性盲区、价值验收、工作区一致性、回退半径和真实外部信号，仍然是本轮成立的必要条件。本轮把验收对象明确推进到工作区和真实使用，并没有消除这些问题：如果目标判据错误，直接检查工作区只会更直接地执行错误目标；如果验收者与执行者共享盲区，换一个 agent 阅读同一份目标文档仍然不能形成认识论独立。

【确定】v0.3 的以下结论应原样保留：主 agent 协调而非代决；计划只能在授权内任务化；交付物版本与消费资格必须绑定；自验只是提交资格；阶段验收必须包含集成和目标对齐；完成度与偏离度不可互抵；人类裁决预算是有限资源。尤其是“版本化交付物—授权消费”这一遗产，正好可以解释本轮“文档先可用、再交给下游”的真实含义。

【推测】本轮真正新增的价值，不是又增加一类文档或一道验收，而是把三个过去容易分开的问题连成一条链：**下游是否有资格使用上游交付物，当前工作区是否真的可被下游使用，最终用户是否能借产物实现自己的目的。** 若只保留文档状态而没有后两者，本轮反而可能从 v0.3 退步为文档流程。

### 1.2 与前两轮的张力及本席修正

第一，v0.2 把错误集收、技能化和分级记忆称作横切机制，本轮却要求经验收敛与模型进化在全量验收后进行。【确定】两者若按字面执行会直接冲突。【推测】应把“横切全程”收缩为**观察、报告、局部纠错、恢复和安全处置横切全程**，把**跨任务泛化、规则晋升、技能化、长期记忆改写以及模型或通用控制流变更**放在全量验收后。不是取消快回路，而是禁止快回路未经审判就变成持久的慢回路。

第二，v0.2 曾把“记忆写回”纳入收敛完成，本轮则把学习放到全量验收之后。【推测】应拆成两个闭合：**交付闭合**由目标义务、真实使用、遗留接受和人类最终裁决构成；**学习闭合**由验收后的归因、拒绝沉淀、候选晋升与再验证构成。项目交付是否完成，不应取决于经验是否已经写回；经验学习是否完成，也不能倒过来改写当时的验收事实。

第三，v0.3 把阶段独立验收主要称作消费门，本轮要求依据目标文档直接验收工作区进度与项目可用性。【推测】这不是多加一项检查，而是扩大阶段验收的因果对象：任务文档只是执行契约，目标文档才是方向锚，工作区产物才是结果对象。阶段门因此不仅是“下游能否消费”，还包括“继续沿这条路线推进是否仍值得授权”。

第四，v0.3 已证明三态不能承载全部控制事实，本轮改为五态并不会自动解决问题。【确定】通过、部分通过、拒绝是判定结果；人工审判是权威路由；待判定是尚无有效判定。五者仍不是同质、互斥、完备的状态机。若强行让它们同时描述文档、任务、阶段和项目，只会把 v0.3 的三态压缩问题扩大成五态压缩问题。

## 2. 完整的“人类—agent 群落—项目工作区”框架

### 2.1 三元结构不是三个平权节点

【推测】三者分别持有**规范权威、受权行动、可检验事实**，不能互相替代。

**人类持有不可转移的规范责任。** 人类决定目的、价值取舍、非目标、风险容忍、重大例外、最终遗留是否可接受，以及什么算项目完成。人类可以委托事实核查和局部判断，但不能用“agent 已验收”转移这些责任。人类的签字本身也不是证据；如果人类只根据主 agent 的摘要批准，规范权威虽然在人，认识过程却已经被摘要控制。

**agent 群落持有受权的认知与执行责任。** 它负责澄清、分解、执行、自验、独立核查、暴露不确定性和保存证据。它的权力来自目标与计划中的明确授权，不来自“我发现了问题”或“我能够修改”。任何 agent 都不能因为参与验收就获得修改判据的权力，也不能因为参与规划就获得降低目标的权力。

**项目工作区同时是环境、协作媒介和证据源，但只是有条件的事实源。** 它能够回答“哪个版本被提交了什么”“谁作了何种声明”“有哪些可复核的产物和记录”。它不能仅凭内部自述回答“目标是否值得追求”“用户是否真正获益”“外部世界是否如报告所述”。工作区里的验收报告也是产物，不是产物正确的自我证明。

【确定】因此，“直接在工作区验收”是必要条件而非充分条件。验收者既要查看被验产物，也要区分**实际观察、可复核证据、执行者自述和验收者推断**。没有这一区分，工作区会从协作黑板变成共同叙事的容器。

### 2.2 角色权限：每次交付只释放下一段有限权力

| 角色 | 应承担的责任与合法权力 | 明确不能单独决定的事 |
| --- | --- | --- |
| 人类／目标所有者 | 确认目标与价值；授权目标和重大判据；处理价值冲突、例外和不可逆风险；接受遗留；宣布最终完成；批准元层进化 | 不能以批准代替实际证据，也不能把最终价值责任交给 agent |
| 主 agent | 对接人类；识别歧义；组织目标文档候选；保留选项、否决和未决分歧；协调交接；提交文档判定 | 不能因掌握表述和摘要而私定目标、软化非目标、批准自己的规范性选择或宣布项目完成 |
| 计划 agent | 依据有效目标版本分解任务；声明依赖、输入版本、任务边界、局部判据和集成义务；提交任务文档候选 | 不能将未裁决假设写成事实，不能为易执行而降低目标，不能借任务化创造新授权 |
| 工作 agent | 在任务边界内执行；形成项目产物候选；自验并报告偏差；标记“执行完毕／已提交” | 不能把自验变成独立通过，不能修改目标或跨任务拓扑，不能把任务提交向上解释为阶段或项目完成 |
| 验收 agent | 对钉定版本作证据判断；依据目标和任务分别检查合规、集成、目标轨迹、当前可用性与风险；提出判定和归因建议 | 不能修补受验对象后继续冒充独立裁判，不能修改判据，不能代替人类接受价值例外或宣布最终完成 |
| 人类与验收 agent 的联合 | agent 提供直接证据和合规判断，人类处理价值、争议、例外与风险接受 | “联合”不等于人类对 agent 摘要再签一次字，也不等于两者可以相互转嫁责任 |

【推测】“文档判定者”不必成为一个永久新增角色。它可以由人类、验收 agent 或获得预授权的下游消费者承担，但必须满足两个条件：判定的是文档对指定用途的可用性，而不是作者的工作量；涉及新目标、新价值、新判据或新授权时，必须回到人类，而不能借“可用性审查”代替规范批准。

### 2.3 目标文档必须过“两道不同的门”

这是本席对主链最重要的补充。

【确定】“人类认可这就是我要的目标”与“这份文档足以让计划 agent 正确工作”不是同一命题。前者是**规范批准**，后者是**用途可用性判定**。人类可能真心认可一个目标，却仍然写得无法规划；一份文字也可能条理清晰、极易执行，却准确表达了人类并不真正认可的目标。

【推测】因此，可用目标基线应由两把钥匙共同释放：

1. 人类对目标、非目标、价值取舍和授权边界的确认；
2. 对当前版本“可否作为规划依据”的可用性判定。

主 agent 可以撰写、提交、标注候选状态，却不应凭作者身份同时独占两把钥匙。这里不是要求人类逐字审批，而是禁止把文字通顺、结构完整或主 agent 自认为清楚，误当作目标已经获得授权。

任务文档则不同：若它严格处于已批准目标与既有授权内，其用途可用性可以在委托权限内判定，不必让每项任务都回到人类。可是，一旦任务化暴露新的价值冲突或需要改变目标，计划 agent 无权以“任务文档已通过”绕过人类。

### 2.4 端到端控制主链

【推测】完整主链应如下理解，箭头表示“授权交付”，不是“完成状态传播”。

**第一步：人类意图 → 主 agent 的目标文档候选。** 主 agent 将意图、非目标、目标使用者、使用情境、约束、价值冲突、未决假设和验收权威表达出来，同时保留被否决选项。此步的产出只是候选，不因文字写完而可消费。

**第二步：目标文档候选 → 可用目标基线。** 经规范批准和用途可用性判定后，某一版本才成为计划 agent 的合法输入。通过只授权在声明范围内规划；部分通过只暴露已经成立且能与未决部分隔离的规划范围；拒绝、人工审判和待判定都不能被默认为完整规划授权。

**第三步：可用目标基线 → 计划 agent 的开发任务文档候选。** 计划 agent 将目标义务映射为任务、阶段、依赖、局部交付和集成义务，并钉定所依据的目标版本。任务文档要同时说明“做什么”和“怎样算这项工作有资格被提交”，但不能用局部可测性替代整体目标。

**第四步：任务文档候选 → 可用任务基线。** 对特定工作 agent 和特定执行用途的可用性成立后，才释放执行权。它证明任务表述和授权足以被消费，不证明任务一定正确，更不证明产物已经存在。若目标版本变化，旧任务基线不能沿用旧结论。

**第五步：可用任务基线 → 工作 agent 的项目产物候选。** 工作 agent 实际改变项目工作区，形成产物、证据、偏差和不确定项。自验通过后只能标记“执行完毕、具备提交资格”。此处的“任务完成”若要保留原词，必须始终带有“执行侧”限定。

**第六步：任务提交与阶段候选 → 阶段工作区验收。** 验收 agent 联合人类，直接依据有效目标文档，辅以任务文档，检查当前工作区中的实际产物。阶段通过释放的是后续阶段对当前集成基线的有限消费权，不是项目完成权。

**第七步：最终集成候选 → 真实使用验收。** 验收对象不是汇报，而是目标用户或代表性使用者为实现真实目的而使用当前产物的过程和结果。测试、演示、文档审查可以提供证据，但不能自动替代使用结果。

**第八步：全量验收与人类最终裁决 → 交付闭合。** 只有目标义务已经闭合或被明确例外处理，真实使用证据与边界清楚，副作用和遗留被披露并由有权者接受，人类才能宣布项目在限定范围内完成。此刻才启动经验收敛与模型进化。

**第九步：全量验收后学习 → 新候选经验／技能／模型／控制流。** 这些是面向未来的变更，不是原交付闭合的隐藏组成部分。任何会影响未来行为的变更都需要自己的验证责任，不能继承原项目验收结论。

### 2.5 五类交付物的关系及“不证明什么”

| 交付 | 判定或验收的直接对象 | 成立后释放的权力 | 即使成立也不证明 |
| --- | --- | --- | --- |
| 目标文档 | 某版本对规划、沟通或验收等指定用途是否可用；规范内容是否获授权 | 在目标范围内规划、协调和作为方向锚 | 目标必然有价值、计划必然可行、项目必然能完成 |
| 开发任务文档 | 某版本是否足以让指定执行者安全、明确地执行，并保持目标追踪 | 在授权边界内执行任务和形成候选产物 | 任务已经执行、产物已经合格、任务集合足以达成目标 |
| 项目产物 | 工作区中的实际内容、集成结果、使用结果与证据 | 经相应验收后成为阶段或最终可消费基线 | 作者自述为真、所有情境都可用、遗留自然消失 |
| 阶段验收结论 | 特定目标／任务／产物版本组合下的合规、集成、方向与当前可用性 | 后续工作在声明范围内消费该阶段基线 | 最终价值已经实现、以后修改不需再验 |
| 总验收结论 | 目标义务、真实使用、偏离、副作用、遗留与人类接受 | 在明确边界内宣布交付闭合并开启后验学习 | 通用控制流已进化、外部环境永久适配、后续变更仍已验收 |

【确定】这五类对象不能共享一个“完成”定义。目标文档的“通过”甚至发生在执行之前；如果它能沿链条自动变成项目“通过”，那么时间在逻辑上就不成立。

## 3. 文档可用性与五态语义

### 3.1 可用性不是文档的内在品质，而是一种关系

【推测】任何一个文档判定都至少要有六个所指：**对象、版本、消费者、用途、判据、证据**。可以写成概念关系：

> 判定 J = 对文档 O 的版本 V，在消费者 C 为用途 U 使用时，依据判据 K 和证据 E 得出的可用性结论。

缺少其中任何一项，“通过”都可能被偷换。某目标文档可以足以支持问题澄清，却不足以授权高风险执行；某任务文档可以足以让原作者继续，却不足以让陌生工作 agent 接手；某文档可以是内容真实的研究记录，却不是合格的任务输入。它们并不矛盾，因为用途不同。

【确定】版本修改后，旧判定不能无条件附着于新内容。即使文件名不变，验收对象的所指也已变化。文档通过也不等于文档中的每个经验命题都真实；它只表示在声明用途下，文档提供了足够可靠、明确和获授权的依据。

### 3.2 三类交付物的“可用”分别意味着什么

**目标文档的可用性，是决策与方向可用性。** 它应使计划者能够识别要服务谁、为何值得做、什么在范围内、什么明确不做、哪些约束不可突破、哪些假设仍未裁决、最终由谁接受价值和遗留。其质量不能只用章节齐全衡量，而应看下游是否需要私自补充关键意图。目标文档可以保留开放性，但开放之处必须成为显式探索对象，不能被计划者静默填成事实。

**开发任务文档的可用性，是受权执行与交接可用性。** 它应使执行者知道所依据的目标版本、任务边界、输入、依赖、交付对象、局部完成判据、集成责任、偏差出口和禁止事项。其关键不是把任务写得越细越好，而是降低“解释负债”却不隐藏必要上下文。过细会替代执行者判断并膨胀维护成本，过粗会迫使执行者猜测；两者都不可用。

**项目产物的可用性，是目的实现与结果可依赖性。** 它不是“文档可用性”的同义词。即使产物本身是一份文档，也要同时区分：它作为某用途文档是否通过五态判定，以及它作为项目结果是否经真实使用证明适合目的。目标文档、任务文档可以非常可用，项目产物却完全失败；反之，偶然可用的产物也不能倒证其交付文档曾足够可靠。

【推测】文档可用性的最低检验应是“陌生消费者能否在不求助作者、不读取私密对话的情况下，作出授权范围内的正确下一步”。但这不是要求工件承载全部背景；若为了使文档完全自足而复制整个项目，解释负债只是转化为阅读负债。可用性追求可控负债，不追求零上下文。

### 3.3 五态的严格语义

#### （1）通过

【推测】通过表示：**当前版本在声明的消费者、用途和判据范围内，已有足够依据被视为可消费。** 它释放有限使用权，不表示普遍正确、全部目标达成或后续版本继续有效。通过必须能回答“准许谁依据它做什么”，否则只是赞美词。

#### （2）部分通过

【推测】部分通过表示：**当前版本存在可清楚划定、且不依赖未通过部分的可用子集，同时其余范围未获得同等消费资格。** 它不是“总体不错”，也不是一个可向上平均的百分比。部分通过的核心是范围边界：哪些判据成立、哪些不成立或未知、允许何种受限消费、禁止何种外推。若所谓可用部分仍暗中依赖失败部分，就不能称为独立可用子集。

#### （3）拒绝

【推测】拒绝表示：**已有足够依据认定当前版本不适合声明用途。** 它是积极的否定判断，不是“作者还没写完”，也不是“评审者暂时没空”。尚未提交的在制品属于工作生命周期；若以完整候选身份提交而缺少强制内容，则可以因对该用途不可用而被拒绝。拒绝针对版本和用途，不天然归罪于执行者，原因可能在上游目标或判据。

#### （4）人工审判

【推测】人工审判表示：**当前问题超出 agent 的授权裁决范围，需要由有权人类处理。** 它主要是权威状态，不是证据强弱状态。证据可以非常充分，但涉及价值冲突、目标变更、风险例外或权限边界，仍然必须人工审判；反之，证据不足并不必然需要人类，可能只是待判定。人工审判不能被解释为通过，也不能成为一个没有具体问题、责任人和裁决对象的停车场。

#### （5）待判定

【推测】待判定表示：**尚未形成对当前版本和用途的有效判定，常见原因是尚未审查、证据不足或关键事实仍不确定。** 它既不等于弱通过，也不等于弱拒绝。若缺的不再是事实，而是有权者作价值选择，则其核心已经是人工审判；若两者并存，单一展示标签不足以保留下钻事实。

### 3.4 五态为何不能独自成为完整状态机

【确定】通过、部分通过、拒绝是结论；人工审判是裁决路径；待判定是结论缺席。把它们画成一个平面五态机，会混淆“答案是什么”“谁有权回答”“现在有没有答案”三个问题。

【推测】仍可以保留用户指定的五态，但应把它视作**文档可用性审查的对外判定词表**，而不是全部内部控制事实。每次显示一个词时，都必须能下钻到版本、用途、范围、证据、判定者和未决原因。这样不是暗中增加第六态，而是拒绝让展示标签承担它不能表达的语义。

### 3.5 文档、任务、阶段、项目必须分轴

| 维度 | 核心问题 | 不能由什么替代 |
| --- | --- | --- |
| 文档判定 | 这个版本对这个用途能否被消费？ | 作者写完、任务执行进度、项目完成度 |
| 任务执行 | 工作是否开始、受阻、中断、执行完毕或失效？ | 文档通过、自验通过、阶段验收 |
| 任务独立结论 | 提交产物是否满足任务契约，证据是否足够？ | 工作 agent 的“任务完成”标记 |
| 阶段进度 | 当前已交付和未交付义务处于什么位置，下一合法动作是什么？ | 完成任务数量占任务总数的比例 |
| 阶段验收与当前可用性 | 局部结果是否集成，是否仍沿目标轨迹，当前是否可供指定下游使用？ | 逐任务合格清单、执行者汇报 |
| 项目完成与价值 | 目标义务是否闭合，偏离和副作用如何，真实使用是否支持目的，遗留是否被接受？ | 阶段全过、文档全过、任务全绿 |
| 学习与进化 | 哪些观察可以泛化，哪些持久行为需要变更并重新验证？ | 一次项目验收通过或错误数量 |

【确定】若只保留五态，将至少丢失：草稿与拒绝的差别、待补证据与待人裁决的差别、通过范围、版本失效、任务阻断与挂起、自验提交与独立验收的差别、阶段集成状态、目标偏离、真实使用边界以及遗留接受。上述任何一项都可能改变下一步是否合法。

一个完整的反例足以说明禁止状态继承的必要性：目标文档通过，只说明可以规划；任务文档通过，只说明可以执行；工作 agent 标记任务完成，只说明执行侧提交；阶段验收通过，只说明某集成基线可被下一阶段消费；项目完成还需要真实使用和人类价值裁决。前一环不是后一环的充分条件。

## 4. 三层验收：分工、证据与权限

### 4.1 工作自验：证明“我完成了受权工作并愿意接受审查”

【确定】工作自验的直接依据是任务文档，同时不能失去对相关目标约束的可见性。其证据包括实际产物、执行范围、所做核查、已知偏差、未决不确定性和超授权事项。它回答的是执行完整性、证据齐备性和提交资格。

【确定】它无权独立证明任务合规，更无权证明阶段集成和项目价值。最稳妥的概念命名是“执行完毕／候选已提交”，而非不加限定的“任务完成”。即使保留原措辞，也必须在任务执行轴内解释，禁止汇总器把它直接累计成“目标完成百分比”。

### 4.2 阶段工作区验收：同时回答五个问题

【推测】阶段验收不应是任务验收的简单加总，而应分别回答：

1. **局部合规**：各任务声明的义务是否有直接证据支持，偏差是否被隐瞒？
2. **跨任务集成**：分别合格的部分放在一起是否形成可用整体，接口处的责任是否有主？
3. **目标轨迹**：当前结果是否仍在实现有效目标，还是只在忠实执行一个已经偏离的计划？
4. **当前可用性**：声明的下游消费者能否在当前工作区中实际使用这一阶段的集成结果？
5. **剩余风险与副作用**：哪些非目标被侵犯，哪些假设未证实，哪些遗留会随进入下一阶段而扩大？

验收 agent 必须读取目标文档本身，而不是只读计划 agent 对目标的转述；必须查看实际项目产物，而不是只读工作 agent 的汇报。任务文档用于确定局部契约，目标文档用于判断方向，工作区用于检验事实，三者不可互相吞并。

人类在阶段验收中的必要作用，是处理价值偏离、重大例外、争议与风险接受，而不是对每个可核验事实重复签字。阶段结论必须绑定当时的目标、任务和产物版本；阶段之后发生实质修改，旧结论不能自动覆盖新整体。

### 4.3 最终真实使用验收：从“符合描述”走向“适合目的”

【确定】演示是执行者选择并展示一条有利路径；测试是检查预先声明的断言；文档审查是判断表述与证据；真实使用则是使用者为了完成自己的目标而实际依赖产物，并承担使用过程中的理解、操作、错误恢复和结果消费。四者可以互相补充，但不能自然等价。

【推测】真实使用至少应保留三个特征：使用目的来自目标而非作者想展示的卖点；使用者不是仅替执行者复述操作的人；验收关注实际结果和代价，包括不理想路径、可理解性、错误后果与遗留，而不只关注成功截图或一次理想输出。

“在工作区进行真实使用验收”需要收缩解释。**工作区应是受验产物与证据的共同入口，不应成为真实性的替代定义。** 如果目标情境就在工作区内，实际使用可以直接支持目标结论；如果目标涉及外部用户、外部系统、长期效果或工作区无法复现的条件，工作区内使用只能支持一个受限命题，不能证明外部就绪。

真实使用能证明的是：在特定版本、情境、使用者和任务范围内，产物曾实际支持某些目的，并暴露了某些代价。它不能证明所有用户、所有路径、长期价值、未发现风险或未来版本。最终接受这些证据边界与遗留的人，只能是获得授权的人类；验收 agent 可以报告和反对，但不能自行接受价值损失。

### 4.4 “全量验收”的最低含义

【推测】全量验收不等于“所有曾写下的任务均打勾”。它至少包括：

- 现行有效目标及其沿革明确，原始承诺与正式变更都能被解释；
- 每项仍有效的目标义务已经满足，或由有权者明确豁免、缩减或作为遗留接受，不能靠删除任务消失；
- 必要的阶段集成结论对应当前最终候选，而非只对应历史版本；
- 最终产物经过目标所要求的真实使用验收，并说明证据外推边界；
- 完成度与偏离度分别报告，阶段全绿不能抵消目标偏离；
- 非目标、副作用、未解决异议、已知限制和剩余风险均已呈现；
- 有权人类明确接受遗留并宣布项目在限定范围内完成。

【确定】经验收敛和模型进化不属于“完成全量验收”的前置项，而是其后续动作。否则“全量验收后才学习”会形成循环定义。全量验收是学习的触发门，不是学习完成后的追认。

【存疑】当真实价值需要很长时间才能显现时，人类必须决定全量验收是只覆盖当前可观察义务并显式接受长期未知，还是保持项目未闭合。框架不能一方面宣称真实价值必要，另一方面用一次短期使用冒充长期结果。

## 5. 全量验收后的经验收敛与模型进化

### 5.1 开发期冻结的准确边界

【推测】“延后进化”应冻结的是**持久化、泛化、跨项目或改变权威的行为变更**，而不是项目内的认知更新与纠错。

开发期必须仍可发生：显式错误和不确定性报告；任务内返工；计划层修正；必要时回目标重订；阻断、停止、回退到已批准基线；安全处置；为防止当前任务重复损害而设置的局部、临时、可审查限制。项目内的计划修正也不等于通用控制流进化，否则任何 r2 回退都会被误禁。

开发期应延后：把一次错误泛化为跨任务规则；晋升普遍约束；形成或修改可复用技能；改写长期记忆；修改模型或通用控制流；改变角色权限、人类门禁和验收独立性。 Agent 在当前推理中理解新事实不是“模型进化”，把这种正常认知也禁止会使框架无法运作。

### 5.2 延后的收益与代价

【推测】收益有四点。第一，验收基线不再被项目中的自我修改持续移动，因果归因更清楚。第二，局部偶然错误不易在压力下立即制度化。第三，交付权与改元权分离，避免 agent 借学习扩张自身权限。第四，验收后可以对照完整结果判断哪些经验值得保留，而不是只根据局部情绪或近期失败沉淀。

代价同样实在。相同错误可能在不同任务重复；观察台账可能膨胀、冲突和重复；现场语境到项目末端已经丢失；人员或 agent 可能把“以后收敛”理解成“以后有人负责”；全量验收后缺乏预算，学习永远不开始；持续型项目没有明确终点，永久延后会让进化机制名存实亡。

【推测】补偿方向不是提前晋升规则，而是开发期保留足够的观察、上下文、反例、已试处置和未决归因，并允许局部止损。记录越充分不等于规则越多越好；开发期应“广收观察、严限泛化”。

### 5.3 例外不能被用作隐形进化通道

【推测】安全例外只应覆盖防止当前损害所必需的停止、隔离、回退和最小限制。若确需跨任务改变持久行为以避免重大风险，就不能再以“普通纠错”为名绕过人类与再验证；它应被视为一次非常变更，并重新界定受影响的验收责任。

【存疑】哪些局部临时约束可由计划或工作层自行设置，哪些跨任务限制必须立即请人，是权威与风险预算问题，材料没有给出答案。不能由本席以概念推演替人类预设。

### 5.4 验收后的学习顺序与再验证责任

【推测】全量验收后，应先保存已验收项目基线及其证据边界，再对观察作去重、归因、反例检查和适用范围判断。归因必须允许“无法确定”和“决定不泛化”，否则台账会把所有偶然事件强行加工成经验。技能化、长期记忆、模型和控制流变更应有不同的影响半径，但都不能仅凭出现频率自动晋升。

验收后会出现三类变化，责任不同：

1. **只形成未启用的候选经验**：原项目验收事实不变，但候选经验在影响后续项目前需要自己的准入判断。
2. **改变未来 agent、技能、记忆或通用控制流**：产生的是新行为主体或新控制器候选。旧项目仍可作为“当时基线曾通过”的历史事实，却不能证明新控制器已验收。
3. **改变项目产物或其关键使用条件**：原验收结论对变更后的对象不再自动有效，必须根据变化与目标义务的因果关联承担新的验证责任。

再验证不应机械等于每次全部重做，也不能机械宣布“只改了一点所以无需验证”。【确定】原则是**证据不能跨越它未曾检验的行为变化自动继承**。【存疑】具体需要多大范围的再验证，取决于变更影响、可逆性和风险，需由相应权威裁决。

如果验收后发现原证据本身失真或当时结论错误，应重新打开原验收问题，而不是把它包装成一次正常“进化”。学习与纠错在此处再次交叉，但不能靠术语改变历史。

## 6. 优异点及其成立条件

1. **【推测】把“写完”改为“可消费”，能显著降低交接中的私有解释。** 成立条件是判定绑定版本、消费者和用途，并通过陌生消费者检验；否则只是增加盖章。
2. **【推测】目标文档—任务文档—项目产物三层分离，使计划偏差与执行偏差可被区分。** 成立条件是计划不得私改目标，且产物验收能同时看到目标与任务；若三层只是复制文本，反而增加漂移。
3. **【推测】自验、阶段验收、真实使用验收分工，覆盖了执行完整、集成可用和整体价值三个不同失败面。** 成立条件是后两层拥有直接证据和独立否定权。
4. **【推测】阶段直接依据目标检查工作区，可把目标偏离在末端之前暴露。** 成立条件是目标版本沿革清楚，阶段验收不止核对清单。
5. **【推测】最终真实使用使“合同全过但没人能用”成为可见失败。** 成立条件是使用者、目的和情境具有代表性，且不将工作区内结果过度外推。
6. **【推测】开发期冻结持久进化，有利于稳定验收对象和约束 agent 自我扩权。** 成立条件是局部纠错、安全处置与观察记录仍然畅通。
7. **【推测】全量验收后再收敛经验，能从完整结果而非局部成败中选择教训。** 成立条件是现场证据被保留，且验收后确有归因与治理责任。
8. **【确定】该框架提高了过程可见性与执行一致性，却不因此保证认知正确性。** 同源目标理解、同源判据与同源验收仍可能共同犯错；真实结果和人类异议只能打破部分盲区，也不能保证全知。

## 7. 缺陷、适用边界与结构性代价

### 7.1 固有缺陷

【推测】第一，文档可用性本身很难在消费前完全判断。一份任务文档看似清楚，真正的歧义可能只有执行时才暴露；因此文档门最多是降低风险，不能证明下游不会误解。

第二，三类交付物会让系统把精力从项目产物转移到“证明文档可用”。如果度量通过率和文档完整度，主 agent 与计划 agent 会优化可判定外观，而非目标价值。

第三，目标与任务并非总能干净分层。探索、研究和创意项目中，任务执行会反过来发现目标本身；过度前置会让正确答案因不符合旧文档而被拒绝。

第四，工作区真实使用存在代表性上限。工作区越可控，越可能偏离真实世界；越追求真实，越难保持稳定基线与清楚归因。这是不可消除的张力。

第五，角色独立主要是程序独立。四个 agent 若共享模型、材料和目标解释，可能只是在四个窗口重复同一前提。增加角色不能自动增加认知多样性。

第六，学习冻结把重复错误和台账成本集中到项目内，把归因与再验证成本集中到项目后。如果项目持续没有末端，或人类只在开发期愿意投入注意力，这一时序会失效。

### 7.2 适用与降级边界

【推测】完整框架适合目标义务较明确、任务可分解、产物可实际使用、跨阶段集成风险高、需要接手审计、验证成本低于重大返工成本的项目。它尤其适合“任务很多但整体可用性容易丢失”的工程。

短而低风险、单阶段、单消费者项目，可以合并目标与任务文档、合并阶段与总验收，只保留有限授权、自验非验收、真实使用与人类最终责任。高度探索项目应把目标分成稳定价值边界与可演化假设，不能假装所有判据都能预先固定。真实反馈迟缓的项目必须显式限定验收结论。验证成本极高的项目若仍逐项重复验收，流程会耗尽价值；但高风险、不可逆项目不能仅以“成本太高”为由删除人类和真实证据。

【存疑】极小项目能否完全省掉独立验收、哪些高风险领域反而需要比本框架更强的外部权威，材料不足以给通用答案。

## 8. 冗余环节与可简化项

### 8.1 必要制衡，不应当作重复删除

- **主 agent 与验收 agent**：前者组织目标和交接，后者对证据作独立判断，权力来源不同。若主 agent 能凭摘要最终验收，就形成信息构造与判定合一。
- **工作自验与独立验收**：前者暴露执行者已知问题，后者挑战执行者未意识到的失败。二者重复检查某些项目是有价值的，不是纯浪费。
- **阶段验收与总验收**：前者防止错误沿阶段放大，后者检查组合后的目标价值。多阶段高集成项目不能只用总验收替代阶段门。
- **目标文档与任务文档**：前者承载规范权威，后者承载受权执行。合并载体可以，合并权力不行。
- **人类多处裁决**：目标确认、例外接受、最终完成、元进化分别保护不同权力，不能为了减少签字全部委托给主 agent。

### 8.2 可以简化而不破坏核心语义的部分

【推测】单阶段项目的阶段验收与总验收可以合并；原子任务的目标文档与任务文档可以共用一个载体，但必须分别回答“为何有权做”和“如何执行”；低风险、授权内的文档可用性判定可由下游消费者承担，不必另设专职角色；可核验事实不必让人类重复签字；验收后经验收敛可复用阶段和总验收证据，不必另起一套汇报。

工作自验与独立验收在低风险、可逆、一次性任务中可以由实际下游消费者的使用验收合并承担，但生产者自证仍不能被称为独立。主 agent 与计划 agent 在小项目中也可是同一执行主体，但不能因此省略从目标授权到任务授权的逻辑跃迁。

真正应删除的是重复汇报、重复状态维护、重复阅读同一摘要和为每道门生成形式相同的新文档，而不是删除不同的失败面。

## 9. 具体失效模式与漏洞

以下 24 条均给出触发机制、后果、严重度和概念级补偿方向。补偿不是技术方案，也不表示风险可以彻底消除。

### F01：主 agent 用“可用文档”吞并目标批准

- **触发机制**：主 agent 同时控制目标表述、选项摘要和通过标记，把结构清楚、易于规划当成人类已经认可。
- **后果**：全链高效执行一个未获授权或被静默改写的目标，后续验收再独立也只在错误契约内独立。
- **严重度**：极高。
- **补偿方向**：规范批准与用途可用性分离；保留被否决选项和未决分歧；主 agent 只能提交，不能独占定稿权。

### F02：文档“通过”被当成脱离用途和版本的固有属性

- **触发机制**：某版本曾供内部讨论通过，之后被用于高风险执行或外部审计；或文档修改后仍沿用旧通过。
- **后果**：消费者继承了自己从未获得的授权，旧证据覆盖新对象。
- **严重度**：高。
- **补偿方向**：所有判定绑定对象、版本、消费者、用途、判据和证据；用途变化与版本变化都需重新界定资格。

### F03：部分通过的通过范围向下游泄漏

- **触发机制**：上游只确认一个可分离子集，下游只见“部分通过”中的“通过”，或把通过比例累计成整体完成度。
- **后果**：未决和失败部分被当作已成立事实，污染任务分解、集成和最终验收。
- **严重度**：极高。
- **补偿方向**：部分通过必须表达明确可用子集及其独立性，禁止将标签投影为全量通过或单一百分比。

### F04：人工审判与待判定互相遮蔽

- **触发机制**：证据不足被送去人类猜答案，或价值冲突被标成待判定以继续收集无关证据；二者又都无明确裁决问题。
- **后果**：人类带宽被事实核查耗尽，价值问题则永久等待；两种“不通过”都无法恢复。
- **严重度**：高。
- **补偿方向**：区分证据缺口与权威缺口，展示标签之外保留未决原因和具体问题，禁止把二者视作同类排队状态。

### F05：草稿、尚未完成与被拒绝混为一谈

- **触发机制**：作者尚未提交就被记为拒绝，或已证明不可用的候选长期留在“进行中”以逃避否定结论。
- **后果**：前者惩罚正常探索，后者掩盖真实不可用性；进度和判定相互污染。
- **严重度**：中高。
- **补偿方向**：工作生命周期与文档判定分轴；拒绝只表达当前版本对声明用途的否定，不表达作者进度或责任归属。

### F06：计划 agent 为可执行而软化目标

- **触发机制**：目标模糊或难测，计划 agent 用容易交付的任务判据替换原有价值义务，并令任务文档顺利通过。
- **后果**：任务全绿恰好证明目标被偷换，偏离被高完成度掩盖。
- **严重度**：极高。
- **补偿方向**：任务化只具派生权；保留目标义务与任务之间的追踪；阶段和总验收直接回到目标及目标沿革。

### F07：任务文档通过被误读为任务完成或产物可用

- **触发机制**：状态汇总只读取“通过”，不看它判定的是执行前文档还是执行后产物。
- **后果**：尚未开始的工作被计为完成，项目工作区空无一物却显示高进度。
- **严重度**：高。
- **补偿方向**：每次判定显示直接对象；文档、任务执行、项目产物使用不同轴，禁止跨对象状态继承。

### F08：工作自验完成逐级滚成项目完成

- **触发机制**：工作 agent 标记任务完成，计划汇总为阶段完成，主 agent 再汇总为项目完成，中间没有独立判断。
- **后果**：执行者的同源盲区被制度化，全绿只代表所有人都提交了自述。
- **严重度**：极高。
- **补偿方向**：将完成限定为执行侧提交；阶段和项目分别需要独立工作区证据、真实使用和人类裁决。

### F09：工作区中的自述被当成工作区事实

- **触发机制**：验收 agent 虽“直接读取工作区”，实际只读执行报告、测试结论或验收文档，不查看其所指产物和结果。
- **后果**：形式上满足工作区验收，实质上仍是汇报验收；伪造或误判被再次引用后看似获得多源支持。
- **严重度**：高。
- **补偿方向**：区分产物、关于产物的声明和独立观察；结论必须能回到实际对象与可复核证据。

### F10：逐任务合格但跨任务组合失败

- **触发机制**：各任务只优化自己的局部判据，无人拥有端到端集成义务，或集成假设只在文档里被声明。
- **后果**：所有任务与文档通过，阶段整体无法被下游使用。
- **严重度**：极高。
- **补偿方向**：阶段验收必须直接检查组合后的工作区和实际下游使用，任务合格不能替代集成结论。

### F11：阶段验收只核对任务清单，丢失目标轨迹

- **触发机制**：验收 agent 以任务文档为唯一依据，避免重新解释目标，却因此也无法发现计划偏离。
- **后果**：偏离直到最终真实使用才暴露，只能高成本回退，甚至因沉没成本被人类勉强接受。
- **严重度**：高。
- **补偿方向**：每阶段同时检查局部契约与有效目标，分别报告完成度和偏离度，禁止相互抵消。

### F12：历史阶段通过污染修改后的最终候选

- **触发机制**：阶段验收后产物或依赖发生变化，最终汇总仍沿用旧阶段结论；局部修复也未评估其跨任务影响。
- **后果**：最终对象从未作为整体被验收，却继承全部历史绿灯。
- **严重度**：极高。
- **补偿方向**：验收结论绑定目标、任务和产物版本；最终全量验收必须指向当前集成候选及其变化影响。

### F13：演示、脚本或执行者代操作冒充真实使用

- **触发机制**：执行者选择理想输入、跳过失败路径、替用户理解输出，或只展示最成功的一次结果。
- **后果**：证明的是产物可被演示，不是目标用户能借它实现目的；易用性和实际价值被高估。
- **严重度**：极高。
- **补偿方向**：以用户目的和实际结果为中心，区分演示、测试与使用，保留非理想路径、使用代价和失败证据。

### F14：工作区内真实使用被过度外推到外部环境

- **触发机制**：受控工作区与目标环境不同，却将一次内部使用表述为外部就绪、长期有效或普遍适用。
- **后果**：验收结论超出证据边界，外部失败被宣称为不可预见，实际上早期声明已越界。
- **严重度**：高。
- **补偿方向**：明确工作区能支持的命题和不能支持的命题；目标若要求外部效果，就需要相应外部结果或限制完成声明。

### F15：“全量”被缩减为任务数量闭合

- **触发机制**：未完成任务被删除、目标被事后改写、遗留藏入非目标，随后宣称所有任务和阶段均完成。
- **后果**：目标义务在账面上闭合，实际承诺与副作用无人承担。
- **严重度**：极高。
- **补偿方向**：以有效目标义务而非任务数为全量锚点；保留目标沿革、豁免、遗留和人类接受记录。

### F16：人类多门签字导致注意力阈值式崩塌

- **触发机制**：每个文档、任务、阶段、例外都要求人类批准，主 agent 又提供高度压缩的推荐摘要。
- **后果**：初期拖延，后期橡皮图章；形式上人类拥有全部权力，实质上放弃了判断。
- **严重度**：极高。
- **补偿方向**：人类集中于规范、价值、重大例外、最终完成和元变更；授权内事实判断委托并保留异议，不以增加签字代替控制。

### F17：“开发期不得进化”被误读为不得纠错

- **触发机制**：发现重复缺陷或安全风险后，因学习冻结而禁止局部返工、临时限制或停止。
- **后果**：已知错误反复发生，损害扩大；团队为交付而隐瞒问题。
- **严重度**：极高。
- **补偿方向**：明确观察、局部纠错、恢复与安全处置始终允许；冻结只针对持久泛化和改元。

### F18：以“局部纠错”为名提前进行隐形进化

- **触发机制**：把跨任务规则、长期记忆、技能或通用控制流修改称为当前项目修复，或借修改任务模板改变通用权威。
- **后果**：验收基线持续漂移，agent 未经人类批准扩大权限，冻结名存实亡。
- **严重度**：极高。
- **补偿方向**：按影响半径、持久性和是否改变权威区分纠错与进化，而不是按作者使用的名称区分。

### F19：验收前台账膨胀并丢失现场，验收后无法可靠收敛

- **触发机制**：开发期只堆积错误标题，不保留上下文、反例和已试处置；或完全相反，所有琐碎观察都进入同一待审池。
- **后果**：重复错误无法去重，末端归因靠事后叙事；学习阶段成本过高而被跳过。
- **严重度**：高。
- **补偿方向**：观察可广收但须保留与判定有关的现场和不确定性；允许不泛化，不能把台账数量当学习成果。

### F20：验收后模型／技能／控制流变更继承旧验收结论

- **触发机制**：系统在全量验收后修改行为，却仍以同一项目“已验收”证明新行为可靠。
- **后果**：旧证据覆盖新控制器，后续失败被错误归因于用户或环境，进化成为免责通道。
- **严重度**：极高。
- **补偿方向**：冻结历史验收的事实边界，把行为变更视为新候选；按因果影响承担新的验证责任，不自动继承。

### F21：多 agent 与多文档制造责任稀释和假独立

- **触发机制**：每个角色只对自己的局部状态负责，所有角色又共享同一模型、摘要和前提；出现整体失败时互相指向上游或下游。
- **后果**：程序活动增加而认知多样性不增，集成与价值成为无人所有的问题。
- **严重度**：高。
- **补偿方向**：明确整体目标与集成的责任归属；承认程序独立上限，引入真实结果和真正的人类异议，而非继续加角色。

### F22：文档自足性要求反成阅读负担与维护污染源

- **触发机制**：为降低解释负债，把全部背景、判据、证据和沿革复制到每份任务文档；目标一变，大量副本需同步。
- **后果**：文档不再可读，版本间冲突增加，执行者转而依赖私聊，形成“文档很全、实际不用”。
- **严重度**：中高。
- **补偿方向**：以消费者完成下一步所需的可控解释负债为尺度，区分权威出处与必要上下文，不以篇幅衡量可用性。

### F23：真实反馈迟缓使全量验收和学习永久无法启动

- **触发机制**：目标价值需长期观察，项目却一直以“尚未真实验收”保持开放；或为了闭合而把短期代理指标当长期价值。
- **后果**：前者冻结进化和责任，后者制造价值假象。
- **严重度**：高。
- **补偿方向**：由人类明确验收时间边界、可观察义务和长期未知；完成声明必须与实际证据同范围。

### F24：门禁指标 Goodhart 化，文档可用性表演取代项目可用性

- **触发机制**：以通过率、返工次数、文档齐全度或阶段数量评价 agent，角色会拆分易过任务、隐藏争议、避免合理拒绝。
- **后果**：流程指标持续改善，真实缺陷与目标偏离下降只在报表中发生；五态越精细，表演空间越大。
- **严重度**：高。
- **补偿方向**：把实际使用结果、未解决异议、偏离和遗留纳入整体判断；保留拒绝和待判定的合法性，不以全绿作为唯一成功形象。

## 10. 最值得保留的最低控制基线

即使对轻量项目大幅裁剪，【推测】以下十条仍不应被静默删除：

1. **人类规范根**：目标、价值例外、最终完成和元层变更不能由执行链自封。
2. **目标双门**：目标内容的授权与目标文档对规划的可用性是两个问题。
3. **钉版与限定消费**：任何文档通过都绑定版本、消费者、用途和范围，旧结论不随文件名自动迁移。
4. **计划仅派生**：任务文档不得为易执行而降低目标，目标义务可追踪到最终验收。
5. **自验非验收**：工作 agent 的完成只表示执行侧提交，不自动形成任务、阶段或项目合格。
6. **状态分轴**：文档判定、任务执行、阶段进度／验收、项目可用性／完成分别报告，完成度与偏离度不互抵。
7. **阶段直接验整体**：依据目标检查当前工作区的集成、方向和下游可用性，而非只核任务清单。
8. **最终真实使用与人类接受**：以实际目的和结果为证据，声明外推边界，由有权人类接受遗留。
9. **纠错与学习分离**：开发期报告、返工、阻断和安全处置不冻结；持久泛化、技能和模型／控制流进化等待全量验收。
10. **进化不继承验收**：全量验收后的任何行为变更都产生新的验证责任，历史结论只适用于历史对象与边界。

这十条的共同点不是“流程更多”，而是**防止权力、证据和状态在不同对象之间无声滑动**。

## 11. 自我反驳：本框架最可能在哪里失效

### 11.1 我可能用分轴解决混淆，却制造了不可维护的复杂性

【确定】本框架要求保留多个控制维度，却没有证明具体团队能负担这些维度。【推测】在短项目里，双门、五态、三类交付物、三层验收和学习后验可能让参与者只维护标签，不再思考产物。若所有项目都照单全收，本席的方案会重演自己批评的“流程完整即质量”。

**反反驳**：分轴不等于每轴一套文档和会议，低维事实可以在同一载体中表达；但【存疑】人类是否愿意接受“概念不可合并、载体可以合并”的纪律，仍需要走查。

### 11.2 文档可用性门可能存在认识论循环

【推测】要判断任务文档是否可用，最可靠的方法往往是让下游真正使用；但若只有使用后才知可用，事前通过就不能提供强保证，只能提供临时资格。这意味着本框架最核心的“先可用再交付”不可能按字面做到绝对。

**反反驳**：将通过降为“当前证据下允许指定消费”，而非“保证不会误解”，可以避免过度承诺；但这样文档门的价值是风险降低，不是质量证明，不能再被包装成硬保证。

### 11.3 程序独立可能不足以支撑我赋予验收 agent 的权重

【确定】本席沿用了前两轮对程序独立和认识论独立的区分，却在阶段与总验收中仍高度依赖 agent 阅读同一目标。若目标文档含有共同错误前提，文档、任务、产物分轴再精确，也可能一致地验错。

**反反驳**：真实使用与人类直接判断是必要的异源信号，但【存疑】代表性用户是否可及、人类是否具备判断能力、真实结果能否及时出现，都没有通用保证。因此本框架最多减少自证，不能承诺消除共同盲区。

### 11.4 “有效目标”可能比框架假定的更不稳定

【推测】探索性项目中，目标变化不是异常，而是主要成果。本框架虽然保留目标沿革和回目标路径，仍偏向先稳定再执行，可能惩罚那些通过产物发现新价值的路线。最终对现行目标验收，还可能掩盖对原目标的偏离。

**反反驳**：双轴报告和稳定价值边界／演化假设分层可缓解，但无法预先解决“新目标是否值得”的权力问题。此类项目应收缩而不是机械套用完整框架。

### 11.5 全量验收后学习的时序可能不适用于持续交付

【推测】如果项目没有公认终点，等待全量验收会使经验和模型进化永远不发生；如果人为切一个终点，又可能只为满足流程而冻结并不完整的系统。本框架对一次性交付闭合的解释强于对持续产品演化的解释。

**反反驳**：可以把明确边界的阶段性真实使用与最终义务闭合作为一个学习周期，但这会模糊“阶段验收”和“全量验收”的区别。【存疑】持续型项目应如何定义全量，是必须由人类重新界定的开放问题，本席不能暗中把任意阶段称为全量。

### 11.6 人类保留最终权力不等于人类能作出好裁决

【确定】把价值和遗留交给人，只解决责任归属，不解决人的知识、时间、偏见和激励。主 agent 仍可通过选项构造影响裁决；真实使用也可能由人类挑选有利用户。

**反反驳**：保留原始证据、异议、非目标和目标沿革能降低摘要控制，但不能保证良好判断。本框架应将“人类裁决有效”作为成立条件，而不是天然事实。

### 11.7 总体反命题

【存疑】如果一个项目的目标清楚、任务很短、执行者与消费者是同一人、工作区产物可直接使用，那么本框架的大部分文档门与角色分离可能都没有正收益。此时最优方案或许只是“人类说明目的—agent 执行—人类实际使用并决定”，五态和多层交付反而多余。本席主张的是高交接、高集成、高责任项目的控制骨架，不应宣称它是所有 agent 工作的普遍最佳形态。

## 12. 最需要人类裁决的问题

1. **五态的地位**：是否确认五态只用于“文档版本对指定用途的可用性判定”，而不是任务、阶段和项目的共用状态机？展示五态之外，是否允许保留版本、执行责任、证据缺口、权威缺口和失效等下钻事实？
2. **目标文档的双门**：人类批准目标内容与判定文档可用于规划，分别由谁承担？主 agent 的“标记交付状态”究竟是提交标记，还是原作者可以单方面给通过？
3. **任务文档的判定权**：在既有目标授权内，谁可判定任务文档可消费；出现何种目标、价值、风险或权限变化时必须回到人类？
4. **部分通过的授权含义**：是否允许其形成受限消费资格，还是仅作报告标签？由谁确认“通过子集”不依赖未通过部分？
5. **任务完成的措辞与权力**：是否同意把工作 agent 的“任务完成”收缩为“执行完毕／候选已提交”，并明确谁有权作任务独立结论？
6. **真实使用的最低真实性**：是否必须有目标用户或代表性使用者？当使用只能发生在工作区模拟情境时，项目完成声明应被限制到什么程度？
7. **全量验收的目标锚与豁免权**：最终应对原目标、现行目标还是二者关系作结论？哪些目标义务可豁免，谁有权接受偏离、副作用和长期未知？
8. **反馈迟缓与持续型项目**：真实价值尚未出现时，项目能否带显式未知闭合；没有自然终点的项目，什么才构成可启动学习的“全量验收”？
9. **开发期冻结边界**：哪些项目内临时约束、计划修正和跨任务安全限制属于合法纠错，哪些已经构成必须延后的经验晋升或控制流进化？紧急例外由谁批准？
10. **模型进化的范围与再验证**：模型选择、提示与先验、技能、长期记忆、角色权限、验收门禁和通用控制流中，哪些被列入“模型进化”；不同影响半径由谁决定再验证责任？
11. **人类裁决预算**：人类愿意在哪些节点作实质判断，哪些事实核验和局部可逆决策可预授权？如何避免主 agent 借摘要和推荐实际控制这些选择？
12. **降级条件**：短项目、探索项目和验证高成本项目分别允许合并哪些载体与角色；哪些最低控制即使降级也不可省略？

## 13. 结论

【推测】本轮最自洽的形态不是“五种状态驱动四角色接力”，而是一个**以人类规范权威为根、以钉版可用文档释放有限授权、以工作区实际产物承接执行、以阶段集成和最终真实使用逐层扩大结论、以全量验收隔开交付与学习**的控制框架。

它最重要的否定性结论是：目标文档通过不证明任务会成功，任务文档通过不证明任务已完成，工作自验完成不证明任务已验收，阶段通过不证明项目有价值，真实使用通过不证明所有情境有效，全量验收通过也不证明验收后进化出的系统仍然可靠。只有把这些“不证明”明确保留下来，端到端交付链才是控制链，而不是完成幻觉的传送带。
