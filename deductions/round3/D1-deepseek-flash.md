## 1. 一句话总判断，以及继承、冲突与修正

### 1.1 总判断

**BRIEF-v3 做对了两件大事——把验收对象从"文档"移到"工作区现状"，把进化推到全量验收之后——但它用同一个"可用性"词同时指称"下游能不能执行"、"项目此刻能不能用"、"目标是否真的被达成"三层，又把五态当作全链通用状态机；如果不把这三层拆成三套判据、三种证据等级与三个判定权属，它会以比 v0.2 更高的自动化程度，重现 v0.2 已经识别的"全绿而不可用"。**

这句话里有两个判断需要立刻兑现，否则它只是修辞：

1. **"做对了"是有条件的。** 验收对象移到工作区，只有在验收方能够**独立复现**工作区中的现象时才成立（证据等级 ≥E2，见 §5.2）；否则"检查工作区"就退化为"读一遍工作区里的文档和汇报"，比逐件验收文档更糟——因为它多了一层"我看了整体"的自我安慰。【确定】
2. **"重现"不是宿命。** 拆层之后，这套构想可以是 v0.2/v0.3 之上的一次真实推进；不拆层，它就是一次自动化程度更高的自证。差别全在一个词上：**"可用"到底是相对于谁的可用。**【确定】

### 1.2 继承 / 冲突 / 修正

BRIEF-v3 说前两轮共识"不是不可修改的法律"，但要求指出冲突、保留必要安全性质、说明是修正还是收缩。我按这三项逐一处理。

#### 继承（不修改，且本轮必须比前两轮更硬）

| 遗产 | 本轮我如何加重它 |
| --- | --- |
| 判据信任根（v0.2 P1） | 本轮延长为**判定者信任根**：不仅判据要有作者，判定也要有具名判定者与判定时的判据版本。 |
| 程序性独立（v0.2 §6.5） | 本轮必须明确"程序性独立"在阶段验收中体现为**冷启动实操**，而不是"换个 agent 读同一批文档"。 |
| 工作区一致性（v0.2 G20） | 本轮升级为**工作区是证据容器、不是事实权威**（§2.2）。 |
| 回退半径 r1–r4（v0.2 §8.3） | 本轮要求五态判定必须携带回退半径，否则"拒绝"无法路由。 |
| 完成度/偏离度双轴（v0.3 §7.1） | 本轮扩展为**三进度向量**（§3.1），偏离度降为其中一个分量。 |
| 证据封存与代次（v0.3 §4.2、§5.4） | 本轮补上一条 v0.3 没有推完的：**判定者也有代次**（§6.5）。 |

| 三态仅作投影（v0.3 §5） | 本轮扩大打击面：**五态本身也只能是投影**（§4.4）。 |

#### 冲突（本轮目标与前两轮遗产正面撞车的地方）

**冲突一：BRIEF-v3"验收 agent 依据目标文档直接检查工作区" vs v0.2"逐条验收 + 集成断言 + 收敛三层"。**

表面是同一件事的两种说法，实质不同。BRIEF-v3 的主语是**目标文档**，v0.2 的主语是**判据集**。若目标文档没有把自身写成可验收的形式（每条义务带可观测现象、验收动作、阈值、反例），那么"依据目标文档检查"在概念上无法执行——你无法依据一篇散文去测量一个状态。

**裁决：修正而非放弃。** "依据目标文档"必须补一个前置条件：**目标文档在通过判定时，就已经包含了验收脚本**（§3.2 的义务表）。否则本条只能降级为"依据判据集检查，目标文档仅提供方向"。这不是文字游戏：它决定了目标文档的"通过"判据里是否必须包含"可验收性"这一项。【确定】

**冲突二：v0.2"错误反馈横切全程" vs BRIEF-v3"经验收敛与模型进化在全量验收后"。**

这是本轮最容易被读成"二选一"的张力。我的判断是：**两者不冲突，但必须把"错误反馈"劈成两半。**

- 横切的是**报告与现场冻结**（一环：观察到什么、期望什么、证据是什么、位置在哪）；
- 延后的是**泛化与晋升**（二环的规则化、三环的改元）。

也就是说，v0.2 的"横切"从来不是"横切地学习"，而是"横切地记录"。BRIEF-v3 冻结的是学习，不是记录。**如果连记录都冻结，延后学习就失去了原料**——到末端只会剩下回忆录。【确定】

**冲突三：v0.2"价值验收不可由执行方自证" vs BRIEF-v3"真实使用验收"。**

这是我认为本轮最危险的一处等价替换。BRIEF-v3 用"真实使用"替换了"价值验收"，仿佛"能用"就等于"该要"。**不能。** 真实使用验收证明的是"这东西在真实条件下可以被使用"，它不证明"这是我们要的东西"。

- 一个登录流程可以用得极其顺畅，而整个产品方向是错的；
- 一个报表系统可以完全满足目标文档里的每一条，而目标文档本身就是老板一时兴起写的。

**裁决：保留价值验收作为独立动作，并把它前移到目标门做一次，而不是只留在末端。** 理由：如果价值只在末端判，整条链都在为可能错误的目标高效服务；阶段验收的价值就在于**尽早把"方向错了"变成可承受的损失**。BRIEF-v3 抽掉了 v0.3 的"目标对齐检查"（§7.2）在阶段层的位置，是本轮的一次退步。【确定】

**冲突四：v0.3"三态仅作对外投影" vs BRIEF-v3"所有文档状态按可用性判定和流转"。**

BRIEF-v3 把五态提升为全链的**流转依据**（"状态根据可用性进行判定和流转"），这比 v0.3 的三态更进一步。但五态混用了三个正交维度（结果、完备度、权属），见 §4.4。**裁决：五态可以保留为对外可读标签，但不得作为唯一的控制事实；它必须附带两个坐标。**【确定】

## 2. 三元结构与端到端控制主链

### 2.1 三个不可转移的责任

BRIEF-v3 把核心结构收缩为"人类—agent 群落—项目工作区"。收缩本身是对的（减少了一层抽象），但三个位置的责任必须说到不可再让渡的程度。

**人类：规范权威 + 唯一的外部真实见证人。**
不可转移的不是"审批"，而是三件事：
1. **定义"什么算达成"**（价值取舍、非目标、可接受的遗留）；
2. **提供只有人能提供的外部信号**——真实使用中的体验、损失、收益；
3. **以具名方式承担完成宣告的信誉责任**。

第 2 条是本节最重要的判断：**在 agent 可以低成本生成任何证据的环境里，证据的稀缺性消失了。** 截图、日志、测试报告、复现步骤，agent 都能批量生产。唯一无法被 agent 伪造的，是"真实世界上发生了某个后果"。而这个信号的唯一来源是人（或外部系统）。因此**最终验收的信任根必须落在人身上，不能落在工作区上**。【确定】

**agent 群落：分类执行 + 分类判定，但不持有规范权。**
agent 可以决定"怎么做"和"这份东西对下游够不够用"，不能决定"要做什么"和"什么算值得要"。这个界线 v0.2 已经画过（验收独立性），本轮要把它画在**验收的对象**上：验收 agent 可以判定"文档能不能被下游消费"，不能判定"目标对不对"。【确定】

**项目工作区：证据容器与协作媒介，不是事实权威。**
这是我对 BRIEF-v3 §3.1 的正面回答。工作区之所以不是权威事实源，理由很朴素：**工作区里的内容也是 agent 写的。** 一个能干的 agent 可以写出一份"看起来完整、看起来通过、看起来有证据"的工作区。若把工作区当权威，等于让被检验方提供检验标准与检验结果。

工作区能提供的是**可复现的现象**（能跑、能读、能按步骤重来）；它不能提供**真**（目标对不对、用户要不要、代价值不值）。所以：

> 权威只有三个来源：可复现的现象、人类具名裁决、真实世界发生的后果。工作区只是前两者的存放处，且它存放的东西本身需要被第三方复现过。

工作区的正确职责清单：承载义务表与覆盖矩阵；承载证据账及其冻结时间；承载否决记录与未决异议；承载失效传播状态；承载未消费差量。这些都是"可被独立复现"或"可被独立核对"的对象，不是"关于世界的断言"。而**唯一不能只凭工作区得出的结论，就是"项目完成了"**——因为完成包含价值判断与外部后果，二者都不在工作区内。【确定】

### 2.2 许可链，不是真理链：每次交付究竟授权了什么

BRIEF-v3 §3.2 问"每次交付究竟授权了什么"。我的回答是：**每一级交付授权的都是"下一步动作的许可"，不是"结论为真"。** 整条链是一条许可链（permission chain），不是一条真理链（truth chain）。

| 交付 | 授权了什么 | **没有**授权什么 |
| --- | --- | --- |
| 目标文档通过 | 计划 agent 可以依据此版本分解任务；验收 agent 可以把它作为验收基准 | 授权目标正确；授权开始执行；授权对外承诺 |
| 开发任务文档通过 | 工作 agent 可以依据此版本执行，并可占用声明的写域 | 授权产物可用；授权跳过自验；授权扩大写域 |
| 任务完成（自验 + 独立判定） | 该候选可以进入阶段验收的集成检查 | 授权可用；授权下游消费 |
| 阶段验收通过 | 下一阶段可以基于此基线继续；下游可按声明范围消费 | 授权目标达成；授权对外交付；授权免除末端验收 |
| 全量验收通过 | 产物可以进入真实使用验收 | 授权宣布完成 |
| 真实使用验收通过 | 目标所有者可以宣布完成（具名 + 遗留清单） | 授权把这次验收结论用于下一代模型/门禁 |

这张表有一个必须说清的后果：**"通过"是有限授权，不是无限背书。** 现实中绝大多数"全绿假象"不是判定错了，而是**授权范围被静默扩大**了——任务通过被读成模块可用，模块可用被读成阶段达成，阶段达成被读成项目完成。许可链的每一跳都有一次范围扩展，而每次扩展都需要一次新的判定，不能靠"反正是同一批东西"接续。【确定】

### 2.3 端到端主链

```
[人类] 口语目标（含动机、非目标、可接受代价）
   │
   ▼
[主 agent] 起草 目标文档 v1
   内容强制含：目标陈述 / 非目标 / 义务表 O1..On（每条：可观测现象·验收动作·阈值·反例·
   证据目标等级）/ 授权边界 / 失败与放弃条件 / 验收脚本草案 / 价值主张（一句话：为什么值得做）
   │
   ▼  ◀── 目标门（人类批准 + 验收 agent 预检"可验收性"）
   │      两条独立判据：①人类确认"这是我要的"（价值）②验收 agent 确认"这可以被测量"（可判定）
   │      ★ 两条都过，目标文档才"通过"；只过一条 → 部分通过（受限消费）
   ▼
[计划 agent] 开发任务文档（任务卡 T1..Tm，每卡：引用义务条 Oi / 判据 / 写域 / 依赖 /
   集成断言 / 回退半径 / 证据目标等级 / 责任租约）
   │
   ▼  ◀── 计划门（验收 agent：义务覆盖矩阵 O×T 无空白 / 判据前置未软化 / 依赖无环 / 写域不冲突）
   ▼
[工作 agent] 执行 → 自验（证据 ≥E2）→ 冻结候选 → 责任状态"待验收"
   │
   ▼  ◀── 任务判定（验收 agent，五态；判定对象＝(候选版本 × 用途"作为集成输入" × 判据版本)）
   ▼
[阶段验收] 验收 agent + 人类，依据目标文档的义务表，直接在工作区做"四查一判"（§5.3）
   │      产出：义务覆盖快照 + 集成断言结果 + 冷启动实操记录 + 剩余风险与遗留 + 偏离度 + 判定
   ▼  （循环：未闭合义务 → 新任务卡；偏离超阈 → 回目标 r3）
   ▼
[全量验收] 六条件（§6.1）
   │
   ▼
[真实使用验收] 人类操作 / agent 记录 / E4 证据导入并封存
   │
   ▼
[人类] 宣布完成（具名 + 未闭合义务清单 + 已接受遗留）
   │
   ▼
[验收后] 经验收敛 → 候选规则 → 人审 → 新基线 + 再验证义务（§6.5）

横切（全程生效，不随阶段结束）：
  责任状态与租约 · 证据冻结与代次 · 判定 TTL · 失效传播 · 一环现场冻结 · 人类裁决预算披露
```

主链上有一句话必须写明：**没有任何一步是"状态自动向上传播"。** 每一跳都是"新对象 + 新判据 + 新判定者"的一次重新判定。这是 §3.3 "不可汇总性"的工程含义。【确定】

### 2.4 角色权限（按"能改变他人义务的能力"划分）

| 角色 | 可以决定 | 不得单独决定 |
| --- | --- | --- |
| 目标所有者（人类） | 目标、非目标、价值取舍、义务表的最终版本、遗留接受、放弃决定、完成宣告 | 不能用签字替代证据；不能把"我批准了"当作"它可用了" |
| 验收使用者（人类，**可能是另一人**） | 真实使用中的操作、体验陈述、收益与损失判断 | 不能替代目标所有者接受遗留；不能在被 agent 引导操作后声称"真实使用" |
| 主 agent | 目标起草、歧义澄清（提供选项）、组织推演、保留分歧、协调交接 | 决定验收什么、决定谁来看、决定验收结论的摘要口径、宣布完成 |
| 计划 agent | 在授权内分解、声明依赖/写域/输入版本/集成断言 | 借分解改变目标；为可落地而软化判据（含**删减义务条**） |
| 工作 agent | 在任务授权内执行、局部次序、自验、申报偏差 | 判定自己"通过"；扩大写域；修改判据；在验收现场"顺手修好" |
| 验收 agent | 对冻结版本做可消费性判定、集成检查、冷启动实操、给出五态与回退建议 | 判定目标价值；修补受验成果后仍任裁判；用"我看过了"代替"我复现过" |
| 人类裁决者（可与所有者重合，须明文） | 人工审判的裁决、例外接受、跨阈偏离的裁断 | 在未读条目上签"确认" |

两处必须加硬约束，因为 BRIEF-v3 没写：

1. **验收 agent 不得由主 agent 临场决定"验收什么"。** 验收清单必须来自目标文档的义务表（在目标门就被人类批准过）。否则主 agent 通过"选择验收范围"就能代决——这是 BRIEF-v3 §4 第一条风险（主 agent 代替人类裁决）的**隐藏入口**：不必篡改目标，只要选择验收哪一段就够了。【确定】
2. **验收现场的任何修复，都使该条目从"通过"降为"待判定"，并生成一条返工。** agent 验收员有极强的"边验边修"倾向，一修，E2/E3 证据就没了，验收就变成了执行。v0.3 有这条（"验收者不得修补受验成果后仍任独立裁判"），BRIEF-v3 漏了，必须补回。【确定】

### 2.5 "人类"不是一个人：六个位置必须分开

BRIEF-v3 全文用"人类"一个词，承担了至少六个不同位置：

1. 目标提出者（动机来源）
2. 目标文档批准者（规范权威）
3. 阶段验收参与者（判定权）
4. 人工审判的裁决者（争议权）
5. 真实使用的使用者（外部信号源）
6. 完成宣告者（信誉责任）

**这六个位置压成一个词，会造成一个具体的、可被利用的漏洞：真实使用验收的目标所有者与验收使用者是同一人时，"真实使用"退化为"自我确认"。** 他既是期待的作者，又是体验的裁判；确认偏倚无法被任何流程消除。而 BRIEF-v3 恰恰把真实使用验收当成了项目的最后一道、也是唯一一道价值关。

概念级补偿：**若"目标所有者"与"验收使用者"为同一人，必须在验收记录中显式声明"自用验收"，并把该次 E4 证据降级标注（记为 E4-self），不得与独立使用者的 E4 混算。** 同时，如果存在真实外部使用者，**外部使用者的一句抱怨的证据价值高于所有者的一小时顺畅操作**。【推测，但方向确定：因为它决定了 E4 是不是外部信号】

这直接回答 BRIEF-v3 §3.7 的"谁有权接受遗留与宣布项目完成"：

> **接受遗留：目标所有者。宣布完成：必须是未参与执行的人；若目标所有者亲任，则必须具名、必须列出未闭合义务、必须声明其证据等级，且不得声称"独立验收"。** "宣布完成"是一个信誉行为，不是一个事实判定；把它包装成事实判定，是整个体系最后也最贵的一次自欺。【确定】

## 3. 交付关系：文档、产物、阶段验收、总验收

### 3.1 三种"可用性"必须分名

这是本席全部推演的枢纽。BRIEF-v3 用"可用性"串起三层，但三层是三个不同的谓词：

| 层 | 谓词 | 回答的问题 | 判定者 | 相对谁 | 失效方式 |
| --- | --- | --- | --- | --- | --- |
| 文档层 | **可消费性**（consumability） | 下游 agent 能否在**不追问作者**的情况下，产生正确的下一步？ | 验收 agent（+必要人裁） | 指定的下游角色 | 文档改版、下游角色变化 |
| 阶段层 | **可操作性**（operability） | 此刻在工作区里，一个陌生人能否**真的完成**一条目标要求的任务路径？ | 验收 agent 实操 + 人类 | 未参与的执行者 | 集成断裂、依赖失效、环境变化 |
| 项目层 | **可使用性 / 达成收益**（usability / benefit） | 真实使用者在真实任务中，能否**不借助作者**获得目标收益？ | 真实使用者（人） | 真实世界 | 场景变化、目标漂移、外部条件 |

三者不可互相推出：

- **可消费 ≠ 可操作**：任务文档可以写得完美无歧义（下游完全能执行），而执行出来的东西拼不起来。
- **可操作 ≠ 可使用**：一个能按文档跑通的系统，可能没人愿意用、或用了没收益。
- **可使用 ≠ 目标正确**：用得顺，方向可能全错。

因此：**"所有文档的状态根据可用性判定"这句话，如果"可用性"指第一层，是对的；如果暗含第二、三层，就是本轮最大的概念滑坡。** 一份任务文档可以 100% 通过（完美可消费），而它描述的整个工作毫无价值。全链没有任何一个门在检查这件事，因为每一层的判据都是相对上一层的"够不够用"。

我把它记成一个可复用的判据：

> **任何"通过"都必须回答"相对于谁的通过"。** 不带相对者的"通过"是非法状态。带相对者的"通过"不能跨相对者复用。

### 3.2 三件套：把"依据目标文档检查工作区"变成可执行的动作

BRIEF-v3 要求"依据目标文档直接检查工作区"。这句话若不加物化，实际执行时会退化成"读一遍目标文档，再读一遍工作区里的汇报，然后说'看起来对得上'"。要让它可执行，目标文档在通过时就必须已经包含三份表。【这是我本席最核心的建设性主张；我认为它是【确定】必需的，但具体形态是【推测】】

**表一：义务表 O（Obligation Register，写在目标文档内）**

| 字段 | 含义 | 为什么不可省 |
| --- | --- | --- |
| Oi | 义务编号 | 提供跨阶段稳定的索引；这是"进度"唯一合法的计数单位 |
| 可观测现象 | 满足时，观察者**看到什么** | 把形容词换成现象；"流畅"不可观测，"点击后 1 秒内出结果"可观测 |
| 验收动作 | 谁、在什么环境、做什么、看到什么算成立 | 这是"验收脚本"的本体，也是冷启动实操的输入 |
| 阈值 | 成立的数量/质量界线 | 没有阈值，判定必然滑向解释权之争 |
| 反例 | 什么样算不成立（最容易的伪装） | **反例比正例更防伪**；只写正例的判据会被低成本满足 |
| 权重 | 该义务在价值上的重要性 | 决定"部分通过"能不能被接受；无权重则所有义务等价，等于没有优先级 |
| 证据目标等级 | 该义务在何层验收时要求 E0–E4 | 见 §5.2；这一列是"证据断层"的事前防线 |
| 非目标边界 | 该义务明确不覆盖什么 | 防止验收范围被下游扩大解释 |

**表二：覆盖矩阵 M（O × T，在计划门生成，随阶段更新）**

每条目标义务必须至少被一条任务卡引用。空白格必须在计划门被显式解释：要么补任务，要么标"本阶段不覆盖"并计入偏离度。

这条机制直接杀死一类最隐蔽的失败：**任务全绿而义务零闭合。** 触发方式极简单——计划 agent 分解任务时，按"容易做的"分解，而不是按"目标要求的"分解；或者目标文档写完后，义务表根本没被任何人再打开过。此时每个任务卡都有自己的判据、都能通过、都有证据，而目标义务一条也没被映射。**这不叫执行失误，这叫计划与目标的脱钩，而 BRIEF-v3 现有的任何一个门都拦不住它**，因为计划门只看"任务是否可执行"，不看"任务是否覆盖义务"。【确定】

反向不要求：任务卡可以不对应任何义务（支撑性、探索性、重构性任务）。但这类任务**必须显式标注类型并单独计成本**，因为它们的价值不由义务表背书——这是"探索预算"的合法出口，也是防止"所有任务都必须挂在义务上"导致过度僵化的必要裂缝。

**表三：证据账 E（Evidence Ledger，随判定生成）**

每条证据至少记录：等级（E0–E4）、产生者、复现者、冻结时间、指向哪次判定、有效期。**"复现者"这一栏是整个证据账的命门**：如果一条证据没有独立复现者，它就只是 E1。而 agent 极擅长生产"看起来像 E3 的 E1"——步骤写得很详细、截图很齐全、日志很漂亮，但没人真的重跑过。

### 3.3 交付关系图与"不可汇总性"

```
人类目标
  │  (规范化)
  ▼
目标文档 [O 表] ──────────────┐
  │  (分解，受 O 约束)          │
  ▼                            │ (验收基准，钉定版本)
开发任务文档 [T 卡 + M 矩阵] ──┤
  │  (执行)                    │
  ▼                            │
项目产物 [E 账] ───────────────┤
  │                            │
  ├──► 阶段验收 ◀──────────────┘
  │      对象：工作区现状（不是任务清单）
  │      依据：O 表 + M 矩阵 + 集成断言
  │      证据：≥E3（冷启动）
  │
  └──► 总验收
         对象：目标 + 真实世界
         依据：O 表全量 + 副作用 + 遗留
         证据：≥E4（真实使用）
```

**不可汇总性（本席提出的一条硬命题）：项目完成不是任何下层判定的函数。**

证明思路（三条独立理由，任一条成立即足够）：

1. **义务闭合度不由任务完成度决定。** M 矩阵可以完备，也可以完全错位；任务完成度是 T 的属性，义务闭合度是 O 的属性，两者通过 M 相连，而 M 本身可能错。
2. **E4 不由 E3 推出。** 能在受控条件下跑通（E3），不蕴含真实使用者会用、会觉得值得（E4）。这两者之间是**归纳缺口**，不是数据缺口。
3. **遗留接受是价值判断。** "这个缺陷可以接受"不是从证据推出的，是从代价与收益的权衡推出的；没有证据能蕴含它。

因此，任何把"任务状态 → 阶段状态 → 项目状态"实现为聚合器（aggregator）的设计，在概念上必然会制造虚假完成。**唯一合法的连接不是状态传播，而是共享索引**：O 表提供索引，让每个阶段都回答"现在这几条义务到哪了"，而不是"我完成了几个任务"。【确定】

这条命题对 BRIEF-v3 §3.5（"自验完成会不会被逐级汇总成虚假项目完成"）是直接回答：**会，只要架构允许汇总。所以架构必须不允许汇总。** 这不是靠自觉，是靠"项目完成只有一个入口：人类在 E4 证据 + 遗留清单上具名"，而没有任何一条代码路径能自动置为完成。

## 4. 五种文档判定的语义边界

> 说明：以下只给语义与边界，不设计处置策略（BRIEF-v3 §5.4 要求）。凡涉及"接下来怎么办"，我只指出**语义所蕴含的合法动作范围**，不展开流程。

### 4.1 判定对象是四元组，不是文档

BRIEF-v3 说"所有文档的状态"，这在语法上暗示状态是文档的属性。**这是错的，而且这个错会直接生出"旧结论被沿用"的漏洞。**

判定的对象是：

> **（文档版本 v）×（用途 U）×（判据集版本 C）×（判定权属 A）**

- 同一份目标文档 v3，对用途"作为计划 agent 的分解输入"可能**通过**（歧义已消除、义务可分解），对用途"作为验收 agent 的验收基准"可能**拒绝**（义务条缺可观测现象，无法测量）。**此时它不是"部分通过"，而是两个不同判定的结果不同。** 若不区分，就会把一个用途的失败平摊到另一个用途上，或反之把一个用途的成功外溢。
- 版本一变，全部判定失效（v0.3 代次原则）。
- 判据一变，全部判定失效（"旧版本通过后修改仍沿用旧结论"的另一半：判据版本也可能悄悄变）。
- 权属一变（判定者无权作此判定），判定降为"人工审判"。

**"通过"的完整写法必须是四元绑定。** 裸"通过"是非法状态。【确定】

### 4.2 五态逐条定义

| 判定 | 精确语义 | 必要条件 | 常见误用 |
| --- | --- | --- | --- |
| **通过** | 判定动作已发生；v 对 U 满足 C 的全部条目；证据 ≥E3（陌生人仅凭文档可完成 U 而不追问作者）；判定在 A 权限内 | 四元绑定齐备；证据账有条目且复现者独立 | 把"作者写完"当通过；把"没人反对"当通过；把 E1 当 E3 |
| **部分通过** | 判定动作已发生；C 的**钉定子集** P 满足，其余（Q = C\P）不满足或未测；**必须公布 P、Q 与分母 \|C\|** | 分母钉定；范围限定到条目级；消费方声明只用了 P | 把 PARTIAL 当"接近通过"；缺分母；不写 Q，只写"部分完成" |
| **拒绝** | 判定动作已发生；存在**被冻结的可判定候选**；C 中至少一条核心条目被证伪 | **有冻结候选**是前提；"核心"必须先定义 | 把"还没做完"报成"拒绝"；把"判据不成立"报成"执行不合格" |
| **待判定** | **信息不足**：判据已钉定，但证据未齐或判定尚未启动。它是"未测"，不是结论 | 判据存在且已钉版 | 长期滞留；被当成"差不多通过"；被当成"需要人" |
| **人工审判** | **权限不足**：判定动作已发生（或明确无法在授权内发生），存在需人类行使的权力（价值取舍、例外接受、目标/判据变更、争议裁决、不可逆风险） | 携带：已形成的倾向性判断、分歧点、要人裁决的精确问题、不裁决的后果 | 被当成"没有结论"；被当成"停车场"；用"已上报"代替"已裁决" |

### 4.3 三组边界（BRIEF-v3 §3.3 明确追问的三处）

**边界一：拒绝 vs 尚未完成 —— 判据是"有没有冻结的可判定候选"。**

- 没有冻结候选（无提交、无证据、仍在改）→ **不属于五态**，属于**工作/责任状态**（进行中、阻断、挂起、失联）。它不是一个文档判定，是一个执行事实。
- 有冻结候选，判据不成立 → **拒绝**。
- 有冻结候选，但证据不足以判断 → **待判定**。

这条边界极重要，因为它决定了两件完全不同的事会不会被混成一件事：**"拒绝"会触发回退半径判定（r1/r2/r3），"未完成"只触发继续执行。** 把未完成报成拒绝，会导致系统反复回退到方案层，把一个"还没干"的问题当成"方案错了"；把拒绝报成未完成，会导致系统无限重试一个已被证伪的方案。BRIEF-v3 §3.3 问这一条，本质上是问"回退半径会不会被压平"——v0.3 已经指出"错误返回压平回退"是高频失效（v0.3 §10 第 8 条），五态如果不在这里钉死，会重犯。【确定】

**边界二：人工审判 vs 待判定 —— 判据是"信息不足还是权限不足"。**

这两者被混用，会产生两个方向相反的病：

- **把权限问题当信息问题拖**（该人裁的，一直"待判定"）→ 人工审判成为永久停车场。BRIEF-v3 §4 自己列了这个风险，但没给区分标准，所以它必然发生。
- **把信息问题当权限问题上交**（证据还没齐就找人）→ 人类注意力被低价值问题耗尽，阈值式形式化（v0.3 失效模式 17）。

区分标准：

> **待判定问的是"我还需要知道什么"；人工审判问的是"我还需要谁的权力"。** 前者可以由 agent 自己推进（补证据、启动判定），后者不能——它必须由某个人做出一个**有代价的选择**。

所以"人工审判"的正确成分不是"等"，而是"把选择摆到人面前"。一条合格的"人工审判"必须包含：**已形成的倾向性判断（不能只给问题不给观点）、分歧点、可供选择的方案及各自代价、不裁决的后果。** 只写"需要人类确认"的人工审判，是把决策成本外包给人的偷懒，而不是升级。【确定】

**边界三：部分通过 vs 通过 —— 判据是"分母与范围"。**

PARTIAL 是五态里最容易被滥用的一态，因为它给了所有人一个体面的台阶。三条硬约束：

1. **分母必须钉定并公布。** k/n 的 n 是哪一版判据集的 n。**删掉一条难判据，PARTIAL 就变成了 PASS**——这是最廉价、最难发现的造假通道，因为它不需要任何人说谎，只需要"重新梳理判据"。
2. **PARTIAL 不得被任何门禁当作通过条件。** 它只能生成**受限基线**（restricted baseline），受限基线必须带"范围 + 到期/复审点"。无到期的受限基线，就是"部分通过"变成"永久通过"。
3. **消费方必须显式声明它只用了 P。** 否则下游会把整份文档当成立。BRIEF-v3 §4 说"部分通过被下游当成整体通过"，机制就在这里：不是下游恶意，而是 P/Q 的划分没有传递下去。

### 4.4 五态是三维笛卡尔积的投影：缺失的格子

BRIEF-v3 §4 说"五态混合了作者进度、证据质量、判定结果与裁决路由"。我同意，但我要说得更精确，因为精确化才能给出补偿。

五态其实是三个正交维度的压缩：

- **结果维**：{未测，通过，部分，不成立}
- **完备维**：{证据齐，证据不足}
- **权属维**：{本权可结，超权需人}

五态覆盖的点：

| 结果 | 完备 | 权属 | 五态里有位置吗 |
| --- | --- | --- | --- |
| 通过 | 齐 | 本权 | 通过 ✔ |
| 部分 | 齐 | 本权 | 部分通过 ✔ |
| 不成立 | 齐 | 本权 | 拒绝 ✔ |
| 未测 | 不足 | — | 待判定 ✔ |
| 任何 | 任何 | 超权 | 人工审判（挤压）⚠ |
| **通过** | **齐** | **超权** | **无位置** ✘ |
| 部分 | 齐 | 超权 | 无位置 ✘ |
| 不成立 | 齐 | 超权 | 无位置（争议）✘ |

**最后一列里的三个空格是真实存在的，而且不是边角情形。** 至少三类判定天然落在这些格里：

1. **价值性判据通过但需人批**（"技术上满足，但是否接受这个取舍由人定"）；
2. **例外接受**（"允许这条不达标，因为代价不值得"）；
3. **目标变更后的重判**（"按旧目标通过，按新目标需人确认"）。

现在它们只能塞进"人工审判"，而"人工审判"的语感是"还没有结论"。于是产生一个语义事故：**一个已经有明确倾向、只等拍板的判定，被记成"待裁决"，在下游看来等同于"未定"，于是被绕过、被拖延、被当成不需要处理。** 这是"人工审判成为永久停车场"的**结构性原因**，不是纪律问题。

概念级补偿：**五态标签必须携带两个坐标才合法**——`结果` 与 `权属`。即最简合法标签是"通过·需人确认"这样的二元组，或者明文规定"凡超权判定，必须在标签上标注 `待批`，且 `待批` 不等于 `未定`"。这与 v0.3 "三态只作投影"同构，但更进一步：**五态本身也只是投影，因为它把三维压成了一维。** 【确定】

### 4.5 五态与任务完成、阶段进度、项目可用性的区别

这是 BRIEF-v3 §3.4 的核心追问，也是本席额外重点（"断层"）的正面回答。我认为必须有一张"维度表"，并在其中引入一个 BRIEF-v3 完全没有的概念：**进度不是状态，是三个不可通约的比率的向量。**

| 维度 | 承载对象 | 判据 | 判定者 | 可否由其他维度推出 |
| --- | --- | --- | --- | --- |
| 文档判定（五态） | （版本×用途×下游） | 可消费性 | 验收 agent（+人裁） | 否 |
| 任务执行状态 | 任务卡 | 动作是否在推进 | 工作 agent 自报 + 租约 | 否 |
| 任务完成判定 | 任务卡 | 任务卡判据 + 证据 ≥E2 | 独立验收 | **否**（不是自验的函数） |
| 阶段进度 | 阶段 | 三向量（见下） | 验收 agent + 人类 | **否**（不可合成单一数） |
| 项目可用性 | 目标 | 可操作性 + 达成收益 | 人类（E4） | **否**（不由阶段推出） |
| 最终完成 | 目标 | 义务闭合 + E4 + 遗留接受 | 人类具名 | **否**（不可汇总，§3.3） |

**三进度向量（本席主张必须同时报告，禁止合成单一百分比）：**

1. **计划进度**＝已完成任务卡 / 总任务卡。**这是路径进度，最廉价、最容易被当成项目进度。**
2. **义务进度**＝已覆盖义务条 / 总义务条（按权重）。**这是目标进度，是唯一可以对外称"项目进度"的量。**
3. **可用性进度**＝当前冷启动可完成的真实任务路径数 / 目标要求的路径数。**这是结果进度，最贵、最真。**

三者可以严重背离，而每一种背离都是一种特定病症：

| 计划 | 义务 | 可用性 | 诊断 |
| --- | --- | --- | --- |
| 高 | 低 | 低 | **计划与目标脱钩**（M 矩阵空白）：干了很多，什么都没达成。最危险，因为报告最漂亮。 |
| 高 | 高 | 低 | **集成断裂**：每个零件都对，拼不起来。v0.2 的组合性盲区。 |
| 中 | 高 | 低 | **证据虚高**：义务"已覆盖"是声明式覆盖（E1 冒充 E3），实操一碰就碎。 |
| 低 | 高 | 中 | **过度设计**：少数义务做得极深，多数没动。 |
| 高 | 高 | 高 | 才具备宣布完成的基础——但仍需 E4。 |

**任何单一"进度百分比"都是在隐藏信息。** 这不是修辞洁癖：一个只报"完成 73%"的项目，无法区分上表前三种情况，而这三种情况的正确处置完全不同（补任务映射 / 补集成 / 补证据）。用一个数回答三个问题，是把决策成本外包给读报告的人。【确定】

而 BRIEF-v3 恰恰只说了"验收进度和项目可用性"两件事，把"进度"当成一个单一概念。**这是本轮构想里最容易被组织惯性填满的空白：一旦有人要求"每天报进度"，系统一定会给出一个百分比，而这个百分比一定是计划进度。** 于是"进度"这个词在概念上被单义化，义务进度与可用性进度永久不可见。

## 5. 三层验收：自验、阶段工作区验收、真实使用验收

### 5.1 分工、证据与权限

| 层 | 主语 | 核心问题 | 证据底线 | 权限边界 | 无权证明 |
| --- | --- | --- | --- | --- | --- |
| **工作自验** | 工作 agent | 我按任务卡做完了吗？我的证据可被复现吗？已知偏差报了吗？ | ≥E2 | 只能产出"候选 + 证据 + 偏差清单"，**原则上不输出"通过"** | 不能证明任务完成，不能证明可消费，不能证明可用 |
| **阶段工作区验收** | 验收 agent + 人类 | 此刻的工作区，能否让一个陌生人按目标文档完成一条任务路径？集成成立吗？义务覆盖到哪？剩余风险是什么？ | ≥E3（冷启动实操）+ 集成断言 ≥E2 | 可判"可消费性"与"可操作性"；不可判价值、不可接受遗留 | 不能证明目标达成，不能证明真实可用 |
| **真实使用验收** | 人类（真实使用者） | 不借助作者，在真实任务中是否获得了目标收益？代价是什么？ | ≥E4 | 可产生 E4；agent 只做环境、记录、清单、反例挑战 | 不能证明"该要"（价值）；不能替代目标所有者 |

一条必须写明的分工原则：**三层的判定者主语不同，不是为了制衡，而是因为三层的证据只能在不同位置产生。** 自验的证据只有执行者能产生（他知道自己做了什么）；阶段验收的证据只有陌生人能产生（他没被作者的路径污染）；E4 的证据只有真实使用者能产生（他在真实条件下）。这不是制度设计，是证据的物理位置。

### 5.2 证据阶梯 E0–E4：把"断层"变成可测的量

BRIEF-v3 反复说"断层"（进度、可用性、目标、证据之间），但从没定义一个可操作的刻度。我给出一个：

| 级 | 名称 | 定义 | 谁能产生 | 成本 | agent 能否伪造 |
| --- | --- | --- | --- | --- | --- |
| **E0** | 声明 | 有人/agent 说"已完成/可用/没问题" | 任何人 | ~0 | 完全可伪造 |
| **E1** | 痕迹 | 有产物、日志、截图、运行记录，但**不可独立复现** | 执行者 | 低 | **几乎完全可伪造** |
| **E2** | 可复现 | 第三方按记录步骤可重复得到同一现象 | 任何第三方 | 中 | 可伪造"步骤"，但需承受复现失败风险 |
| **E3** | 冷复现 | 第三方在**没有作者任何解释**的条件下，只读工作区文档即可复现并完成一条任务路径 | 未参与者 | 高 | 难：需要文档本身自足 |
| **E4** | 真实使用 | 真实使用者在其真实任务中，不借助作者，达成目标收益（含失败与卡顿记录） | 真实使用者 | 极高（需要时间、真实场景、人的注意力） | **不能**（无真实后果） |

**"证据断层"的可操作定义：判定所声称的证据等级高于实际证据等级。**

这个定义的好处是它可以被逐条检查，而不需要争论"够不够充分"。三个最常见的高发点：

1. **文档"通过"声称 E3，实际 E1。** 验收 agent 读了文档觉得清楚（E1 的自我体验），就判通过。真正的 E3 要求：**一个没读过任何对话记录的人，拿着这份文档，能不能产出正确的下一步？** 这一步没做，五态里的"通过"就是空转。**这是可消费性判定最常见的塌陷方式，也是 BRIEF-v3 最可能失败的地方。**【确定】
2. **阶段"可用"声称 E3，实际 E2。** 同一个作者在场，边操作边解释（"这里你要先点这个"），现场是通的——但那不是 E3，那是 E2 加口头补充。**作者在场本身就是证据污染。**
3. **真实使用声称 E4，实际 E3.5。** 脚本化演示、理想路径、执行者代操作、预先铺好的数据。这不是真实使用，这是**受控实操**，它的证据等级是 E3，不是 E4。

**E4 的一个不可消除的性质：它无法在工作区内取得。** 真实使用发生在真实世界，工作区只能承载它的**记录**（日志、录像、用户的陈述、损失清单）。因此：

> 工作区能承载 E4 的**现场与记录**，不能承载 E4 的**真实性**。E4 的真实性只能由人以信誉担保。

这是本席对"在工作区做真实使用验收"最重要的一次语义校正。它带来一个不体面但必须承认的结论：**整个验收体系的最终锚点是一个人的话。** 这不是设计缺陷可以被修掉，这是所有验收体系共同的地基（包括人类的审计、同行评议、临床验证）。能做的只是把这个人**具名、可追责、且必须承担他看过的条目被记录在案**。凡声称"工作区可以替代人的见证"的设计，都是把地基换成了地毯。【确定】

顺带一个附加判断：**在 agent 可以批量生产证据的环境里，E0–E2 的证据价值正在快速贬值。** 因为生成一份"看起来完整、步骤清晰、截图齐全"的产物，边际成本趋近于零。这导致两个后果：(a) "有证据"不再等于"可信"，只有"被独立复现过的证据"才有意义；(b) 验收的重心必须从"检查有没有证据"转向"检查证据能否被一个不知情者复现"。**这条判断对整个 AECW 是普遍的，不只对本轮。**【推测，但方向很强】

### 5.3 阶段工作区验收：四查一判

BRIEF-v3 要求"验收 agent 联合人类，依据目标文档，直接从工作区验收进度和项目可用性"。我把它具体化为四个检查加一个判定。**关键是四个检查的对象都不是"文档"，而是"工作区的现状"。**

**查一：目标对齐（依据 O 表，不依据 T 卡）。**

不是问"任务做完了几个"，而是问"O1..On 各自的覆盖状态是什么、以什么证据等级覆盖的"。这是 M 矩阵的阶段快照。凡"已被任务卡引用但产物未产生"的义务，状态是未闭合；凡"产物已产生但未映射到义务"的东西，是孤儿产物——**孤儿产物不是浪费，它是计划失准的证据**，必须被记录而非被隐藏。

**查二：集成（必须有可执行的集成断言，且断言来自 O 表）。**

这是 v0.2 组合性盲区的直接补偿。但有一个 BRIEF-v3 没注意的细节：**集成断言的来源必须独立于任务文档。** 如果集成断言是由计划 agent 写的、由工作 agent 实现的、由验收 agent 对照同一份断言检查的，那就是三源自证。集成断言必须从**目标义务**推出（"O3 与 O5 组合使用时，行为应当如何"），因为义务是人类的语言，任务是 agent 的语言。这一条决定了集成检查是"真的验证组合"还是"验证自己写的规格"。【确定】

**查三：冷启动实操（本席认为这是阶段验收不可替代的核心，也是"直接检查工作区"的字面实现）。**

定义：验收 agent（或人类）在**不读工作 agent 任何解释**、**不借助作者**的条件下，只读目标文档 + 任务文档 + 产物，在干净环境里，完成目标文档中写明的一条**典型任务路径**，并记录每一步的卡点。

四条硬性要求：

1. **必须由没参与该任务的人做。** 同一个 agent 换个上下文不算——它的先验还带着上次的解法。
2. **失败必须被记录，不得现场修复。** 一修，E3 就退化成 E2。
3. **必须记录"我原本期望什么"，而不只记录"我看到什么"。** 期望与实际的差，就是可用性的本体。只记现象的验收报告，无法区分"设计如此"和"设计没做到"。
4. **卡点必须分级**：阻断（做不下去）/ 摩擦（能做但要多想、多试）/ 困惑（做了但不确定对不对）。**"困惑"是最有价值的一类**，因为它不报错，却会让人悄悄用错。

这条检查之所以是核心，因为它同时覆盖了三件事：可消费性（文档够不够用）、可操作性（东西能不能用）、集成（路径是跨模块的）。而它无法被"读文档"替代——**读文档只能验证文档的自我一致性，不能验证文档与世界的一致性。**

**查四：剩余风险与遗留。**

不可逆动作是否已执行且已记录；未闭合义务清单；已接受的技术债；未决异议；未消费差量（v0.3 的概念，本轮同样需要）；已知失效但未修复的问题。这一查的价值不在于"发现新问题"，而在于**把已知问题变成记录在案的问题**。没有被写下来的风险，会在下一阶段被当成不存在。

**判：阶段判定。**

输出必须是复合的，至少包含：
- 五态判定（对象＝（阶段产物版本 × 用途"作为下一阶段基线" × O 表版本））；
- 义务覆盖快照（含证据等级分布）；
- 冷启动实操记录（含失败）；
- 偏离度（对原目标、现行目标、目标沿革三者的偏离，不可互相抵消）；
- **明确写出"本次通过的范围"与"本次不通过/未检查的范围"**。

最后一项是我要特别强调的：**"不通过的范围"与"未检查的范围"必须分开写。** 二者的危险程度不同——"未检查"更危险，因为它会被默认当成没问题。BRIEF-v3 §4 有"部分通过被当成整体通过"，而"未检查被当成通过"是它的近亲，且更隐蔽，因为没有任何标签会显示它。

### 5.4 真实使用验收：必须拆成三件事

BRIEF-v3 说"最后项目开发完成后，根据目标在工作区做真实使用验收"。这句话里有一个范畴问题，必须拆开。

**范畴问题：工作区不是使用场所。**

工作区是为 agent 协作设计的环境（文档、产物、状态、证据）。真实使用发生在工作区之外——真实用户界面、真实业务流程、真实数据、真实时间里。**除非项目产物本身就是工作区内的工件**（例如本项目 AECW 自身：产物就是文档与流程，其"使用"就是在工作区里被 agent 消费），否则"在工作区做真实使用"在概念上讲不通。

两种解读，后果完全不同：

- **善意解读**：工作区承载真实使用的**现场组织与证据保全**（使用脚本、会话记录、用户陈述、损失清单、失败录像）。此时工作区是**证据容器**，成立。
- **字面解读**：把人请到工作区里操作。此时如果产物是外部系统，人只是隔着显示器操作，工作区退化为"记录本"；如果产物就是工作区内的东西，才真正成立。

**BRIEF-v3 没有区分，而这个区分决定了 E4 的证据等级上限。** 这是我认为本轮必须修的第一处硬伤，但要把两个不同强度的判断分开：

- 【确定】**定义层面**：真实使用发生在产物被使用的地方；工作区是协作环境，二者只有在"产物本身就是工作区内工件"时才重合。这句话是定义推论，反驳只能来自措辞。
- 【存疑】**经验层面**："多数项目的产物落在工作区之外"——这一条我无法从材料推出。若实际上大量项目的产物就是文档、流程、配置、判据模板一类的工作区内工件（例如 AECW 自身，以及任何"以交付文档为产物"的项目），那么"在工作区做真实使用验收"就是常态而非范畴错误，我这一节的批判力度就要下调一大半。**这是本篇最需要被读者用经验反驳的地方。**

拆成三件事，因为它们证明的东西完全不同：

| 动作 | 内容 | 证据等级 | 能证明 | 不能证明 |
| --- | --- | --- | --- | --- |
| **A. 受控实操验收** | 人类按目标文档的真实任务路径，在工作区亲手操作一遍，agent **不得代操作、不得提示、不得预先铺路** | E3（不是 E4） | 可操作性、文档对人类的可读性、路径完整性 | 长期可用、真实收益、场景适配 |
| **B. 真实使用观察** | 把产物投入真实场景使用 N 天/周期，采集使用日志、卡点、放弃行为、损失 | E4 | 真实可用性、真实代价、真实收益 | 需要时间与外部条件；多数跨出项目周期 |
| **C. 验收性试运行** | 以 O 表中的典型任务清单驱动，量化成功率与卡点数 | E3 | 覆盖率与稳定性 | 真实意愿与真实收益 |

**三者的关系：A 是 B 的必要不充分条件；C 是 A 的量化版；B 才是真正的 E4。**

这里有一个我认为必须说清的时间尺度矛盾：**真实使用暴露问题往往需要数天到数周**（用户会绕过、会误用、会在第二次使用时放弃、会在数据量变大后崩）。而"项目开发完成后"的一次性真实使用验收，在时间上只能覆盖第一次使用的头几十分钟。**所以"项目末端的真实使用验收"在概念上无法完成它名字所承诺的事。**【确定】

可行的形态只有三种，各有代价：

1. **验收期（acceptance window）**：宣布"候选完成"，进入 N 天真实使用观察期，期满由人类裁决。代价：项目无法即时收尾，责任悬置。
2. **试用用户先行**：在阶段验收阶段就引入真实使用者做小规模真实使用，末端只做汇总确认。代价：需要外部使用者，且他们有成本。
3. **降低承诺**：明确宣布"本次验收只覆盖受控实操（E3），真实使用验证延后到运行期，由运行期的问题反馈承担"。代价：**诚实但风险后置。**

BRIEF-v3 现在隐含的是第 3 种，但用的是第 2 种的语言。**这是"演示冒充真实使用"（BRIEF-v3 §4）的结构性成因：不是有人作弊，而是验收动作在时间上做不到它被命名的强度，于是所有人默契地降低标准，而名字保持不变。**【确定】

**防伪的最小要求（概念级，不是流程）：**

- **不得由执行方操作**；执行方在场也必须声明"作者在场"，并降级。
- **不得使用预置的理想数据**；必须使用真实或至少未被清洗过的数据。
- **必须记录失败与放弃**，而不只是成功路径。
- **必须记录"人类原本打算做什么"**（意图），因为真实使用中的偏离往往是意图与实现不符，而不是功能缺失。
- **必须记录时间戳与操作者身份**，因为"使用了一小时"和"使用了两周"是两种证据。

### 5.5 "联合人类"的三种形态与披露义务

"验收 agent 联合人类"至少有三种形态，控制性质完全不同：

| 形态 | 做法 | 优点 | 风险 |
| --- | --- | --- | --- |
| 并检（双盲） | agent 与人各自独立判定，再比对 | 独立性最强，能发现 agent 的系统性偏差 | 成本最高（人类要独立做一遍） |
| 复核（人做二审） | agent 先判，人复核 | 成本中等 | 人会接受 agent 的框架（锚定效应），实际变成"给 agent 的报告签字" |
| 人主检（agent 辅助） | 人实操，agent 记录/清单/反例挑战 | 最贴近"真实可用" | 人类带宽是瓶颈；agent 的"辅助"可能变成引导 |

我的判断：

- **阶段验收 → 复核为主，并检用于高风险阶段**（含不可逆动作、含对外承诺、偏离度已超阈）。
- **真实使用验收 → 必须人主检，agent 只能做三件事**：搭建环境、记录、提出反例挑战。**agent 不得提示下一步。** 一旦提示，人就从"使用者"变成"被引导者"，E4 降级为 E3。【确定】

**两种机制，用来防止"联合"变成背书修辞：**

**机制一：人类实际查看条目数（强制披露项）。**

每次验收记录必须写明：本轮人类实际查看了哪几条义务、花了多少时间、跳过了哪几条。**这不是审计，这是防自欺。** 因为"联合验收"最常见的失败形态不是人反对，而是人**没看**——他看了摘要、听了汇报、在结论上签了字。此时记录上有"人类参与"，实质上没有。

一旦"人类实际查看条目数"成为必填项，"人没看"就变成可见事实，而不是隐含假设。这是我为 v0.3 的"人类裁决预算是有限资源"找到的最直接的物化方式。【确定】

**机制二：异步否决窗口。**

人类不必每阶段在场，但每个 agent 作出的验收结论进入一个 **N 小时否决窗口**；窗口内人类可无条件否决，窗口关闭结论才生效。

- 优点：把"人类在场"变成"人类可及"，大幅降低预算消耗，同时保留否决权。
- 风险：**窗口内没人看，就变成默认通过**——这是"阈值式形式化"的温和版本，比明面上的形式化更难发现，因为它没有签字仪式，只有沉默。

补偿：**窗口期内未被查看的条目，必须显式标记为"未经人看"，且不得计入"人类确认"的证据等级；高风险条目不允许走异步窗口，必须同步人看。** 三条缺一不可，否则异步窗口就是给形式化发的许可证。【推测】

**分级是必须的。** BRIEF-v3 说"验收 agent 联合人类在各个阶段完成后"，等于假设人类预算无限。v0.3 已裁决人类注意力是硬预算。**必须按风险分级**：

| 档 | 触发条件 | 人类参与形态 |
| --- | --- | --- |
| L | 低风险、可回滚、纯内部 | agent 判定 + 异步否决窗口 + 抽检 |
| M | 常规阶段 | agent 判定 + 人类复核关键条目（明示几条） |
| H | 不可逆动作、对外承诺、偏离超阈、义务核心条 | 人类同步实操/并检 + 具名 |

## 6. 全量验收的最低含义与延后进化

### 6.1 全量验收的六个最低条件

BRIEF-v3 §3.8 问："全量验收是所有任务通过、所有阶段通过、目标义务闭合，还是包含真实使用、副作用、遗留和人类最终裁决？"

我的回答是：**不是前两个。"所有任务通过"和"所有阶段通过"是过程完备性，不是全量验收。** 一个项目可以所有阶段都通过而一条义务都没闭合（M 矩阵全空）。全量验收的最低含义是六条同时成立：

1. **义务闭合。** O 表中每条义务处于"已闭合"或"已被显式接受为遗留"。**没有第三种状态。** 未闭合且未被接受 = 未达成。注意：接受为遗留需要人类具名，且必须写明代价与影响面。
2. **证据达标。** 每条已闭合义务的证据等级达到 O 表中事先声明的目标等级（多数应为 ≥E3）。**证据等级不足的闭合，是声明式闭合。**
3. **端到端路径 ≥1 条达到 E4。** 至少有一条完整的目标任务路径，被真实使用者不借助作者走通，且记录含失败。
4. **副作用与不可逆动作已清点并被接受。** 包括对外发布、数据删除、外部依赖引入、不可撤回的承诺。
5. **未决异议已裁决或显式搁置。** 包括 agent 之间、验收者与执行者之间、异构模型的异议。**"没有异议"和"异议未被处理"必须区分**——前者是记录缺失，后者是失职。
6. **人类以具名方式承担完成宣告。** 附：未闭合义务清单、已接受遗留、证据等级声明、以及"本次验收未覆盖什么"。

**注意六条里没有一条是"所有任务通过"或"所有阶段通过"。** 这不是说任务与阶段不重要，而是说它们是**必要条件之一，不是充分条件，也不是定义**。把"阶段全过"当全量验收，正是"任务全绿而整体不可用"的机制。

反向也成立：**允许"有任务未完成但项目达标"**——因为任务图是计划，义务是目标。计划没做全而目标达成，是计划的冗余，不是项目的失败。但必须记录：哪些任务被冗余、为什么、代价多少。这防止"为了跑完流程而做无用的任务"。

### 6.2 延后进化的收益

我要明确肯定 BRIEF-v3 这一步，因为它是本轮相对 v0.2 的一个**真实进步**，而不是措辞变化。

1. **给进化环装了天然的节流阀。** v0.2 §6.6 自己承认：进化环不是天然向善的，一次错误归因会被写成预防规则，此后错误被制度化。BRIEF-v3 把进化推到末端，等于规定"项目内不许改规则"，于是**一个项目不可能被自己的错误规则锁死**。这直接切断了"越进化越僵化"的最短路径。【确定】
2. **避免了"规则先于样本"的常见病。** 项目内看到的往往是一次性事件；项目末看到的才是模式。把泛化推后，样本更充分。
3. **保住了开发期的目标稳定性。** 如果开发中可以随时晋升约束，目标与判据会持续漂移，验收基准失效。延后进化等于**冻结基准一个项目周期**，这是可验收性的前提。
4. **降低了归因的责任压力。** 项目内每条错误都要求"立刻总结成规则"，会诱导 low-quality 归因（为了结案而编因果）。延后给了"归因不明 → 观察"的空间。

### 6.3 延后的代价（四条，我认为 BRIEF-v3 低估了）

**代价一：重复犯错的成本是复利的。**

如果同一个错误在项目内出现 5 次，每次都 r1 返工，总成本是 5×；如果允许"本项目内加一条临时约束"，成本是 1× 加一点约束维护。BRIEF-v3 说"允许局部返工"，但如果连"项目级临时约束"也不许，那就是**明知故犯**。

**代价二：现场上下文的半衰期很短。**

错误发生的现场——当时的判据版本、当时的歧义、当时被否决的选项、当时为什么选了这条路——在项目末端已经丢失。经验台账记录的永远是**二手重建**。延后到全量验收后收敛，等于**用回忆录代替现场**。

这不是理论忧虑：任何做过项目复盘的人都知道，复盘时最难的不是"当时发生了什么"，而是"当时为什么觉得那样是对的"。后者才是可学习的部分，而它恰好是最先丢失的。

**代价三：台账规模是超线性的，收敛能力不是。**

延后意味着台账在项目内只增不减。项目结束时可能有几十上百条，且互相冲突、归因不明、上下文丢失。冲突对数是 n²，所以整理成本超线性增长。**于是延后有一个隐性的规模上限：项目越长，验收后越不可能可靠收敛。** BRIEF-v3 §4 自己列了这个风险（"全量验收前经验台账巨大、冲突、失真或上下文丢失"），但没给机制。【确定】

**代价四：末端收敛与项目结束撞车。**

项目结束时人的注意力在"交付"上，不在"复盘"上。把最费脑的收敛放在这个时刻，实际上是把最容易被砍掉的环节放在最容易被砍掉的时间。

### 6.4 开发期必须允许 / 必须延后：判据是"是否随项目失效"

BRIEF-v3 §3.9 问："如何避免把'延后进化'误读成'开发期不得纠错'？"

我给一个可操作的二分判据，比"是否横切"更精确：

> **问：这个变更随项目结束而失效，还是随项目结束而保留？**
> **随项目失效 → 属于控制，开发期必须允许。**
> **随项目保留 → 属于学习，必须延后。**

| 开发期必须允许（控制） | 开发期必须延后（学习） |
| --- | --- |
| 显性错误报告（一环记录） | 跨任务泛化（一次错误 → 通用规则） |
| 局部返工 r1 / 回方案 r2 | 约束晋升（项目约束 → 全局约束） |
| 阻断、挂起、止损、安全处置 | 技能化 |
| **项目级临时约束**（"本项目禁止删除 X"） | 长期记忆改写 / L0–L1 晋升 |
| **台账整理**（去重、合并同源、标注现场已冻结/已丢失） | 控制流、门禁、判据模板变更 |
| **现场冻结**（把错误发生时的判据版本、对话切片、被否选项封存） | 模型/先验变更 |
| 目标变更（r3，走人类门，属规范调整不属学习） | 度量口径变更 |

最后两行"台账整理"与"现场冻结"是我要特别强调的：**它们是控制，不是学习。** 它们不产生任何跨项目的规则，只是把原料保存好。如果不允许在开发期做这两件事，延后学习在概念上就无法成立——因为它到末端时已经无原料可用。

**结论：冻结的是泛化，不是纠错；也不只是纠错——还冻结了"把现场保存好"这件事的反面，即"让现场腐烂"。** BRIEF-v3 的表述容易被读成后者。【确定】

### 6.5 再验证责任与"判定者代次"

BRIEF-v3 §3.10 问："全量验收后修改经验、技能、模型或控制流，会不会反过来污染已验收基线？"

我的回答要硬：**一定会，除非把"验收结论"定义为四元组而不是事实。**

> **验收结论 = f（被判定产物代次，判据版本，判定者版本，判定方法）。任一变化 → 结论过期，不是"仍然有效"。**

v0.3 只说了产物有代次（§4.2）。**v0.3 漏掉的是：判定者也有代次。** 这一条在本轮尤其致命，因为 BRIEF-v3 明确把模型进化放在验收后——**也就是说，它安排了一个"判定者换代"的动作紧跟在"判定完成"之后。** 换完模型，之前所有验收结论的判定者已经不存在了。

再验证义务的分级（概念级）：

| 变更 | 失效范围 | 再验证义务 |
| --- | --- | --- |
| 判据模板 / 门禁 | 所有用该模板的判定 | 重跑**该项目**至少一条端到端路径（E3），并重判受影响条目 |
| 技能 | 使用该技能的任务类型 | 重跑该任务类型的代表任务（E2+） |
| 控制流 / 角色权限 | 全链 | **旧验收结论全部作废**，需重新走阶段验收 |
| 模型 / 先验 | 全链 | **旧验收结论全部作废**；E4 证据可复用（因为它是外部世界的事实），但所有 agent 判定需重做 |

关键原则：**"验收结论绑定四元组"同时意味着"变更不能既宣称改进又宣称继承旧结论"。** 这是最常见的自我欺骗形态："我们升级了模型，所以现在更好；同时之前的验收仍然有效。"这两句话不能同时为真——要么旧结论过期（那就得重验），要么新模型没有改变判定能力（那这次"进化"没有实质意义）。

另一个必须承认的限制：**E4 证据是唯一可以跨判定者代次复用的证据。** 因为它记录的是世界上的事，不是 agent 的判断。这从另一个方向再次确认了 §5.2 的结论：E4 是整个体系里唯一不随 agent 换代而失效的东西，因此它必须是终点，也必须是锚点。【确定】

## 7. 优异点、缺陷、冗余与可简化

### 7.1 优异点及成立条件

**优一：把验收对象从"文档"移到"工作区现状"。** 这是本轮最强的推进，而且是真的推进，不是措辞。

v0.2/v0.3 的验收对象都是产物或交付物，逐件验收，因此必然带组合性盲区（v0.2 反复承认的最大漏洞之一）。BRIEF-v3 说"直接从工作区验收"，验收对象变成**多个产物的组合态**。这在概念上把"集成"从一道附加检查提升为验收的本体。**如果做到，它是 v0.2 组合性盲区的结构性解药，而不是补丁。**

成立条件：验收方必须能**独立复现**工作区中的现象（≥E2），并且做**冷启动实操**（≥E3）。做不到，这个优点立刻反转为缺点——"检查工作区"变成"读一遍工作区里的文档和汇报"，比逐件验收更糟，因为它多了一层"我看了整体"的自我安慰。【确定】

**优二：把"进度"和"可用性"分开问。** "验收进度和项目可用性"这两个词并置，隐含了"进度高 ≠ 可用"的判断。方向完全正确——尽管它停在了一个词的层面，没有展开成三向量（§4.5）。

**优三：经验收敛延后，给进化环节流。** 见 §6.2。这是对 v0.2 "进化一等公民"的一次健康反向修正，而且修正的是 v0.2 自己承认的最深风险。**能自我否定上一轮的最强主张，是本轮最值得肯定的一件事。**

**优四：把"人工审判"设为一个一等状态，而不是异常路径。**

v0.3 的"人类门禁"是**流程节点**（一个门）；BRIEF-v3 把它变成**文档的一个可能状态**。这个转换有真实价值：某文档长期处于"人工审判"变成**可观测、可统计、可追责**的事实，而不是"这个流程走得慢一点"。**它把人的缺席从"沉默"变成"记录"。**

但注意：它同时把"人没看"合法化了（见 §5.5 的机制一），所以这个优点必须配披露义务，否则是双刃。

**优五：五态里有"部分通过"。** 相对二值判定是进步：它承认"k/n"是真实存在的状态，给执行者一个不说谎的出口。没有 PARTIAL，执行者只有"硬做"和"隐瞒"。v0.2 已指出这点（G14），BRIEF-v3 保留下来是对的。

**优六：主链角色收缩为四个 agent + 人类。** v0.3 有八个角色（含观测程序、异构模型），BRIEF-v3 收缩为四个。**角色少不一定控制弱**——如果每个角色的边界清楚，少角色反而减少责任稀释。这是一次有价值的简化。

成立条件：被砍掉的"观测程序"与"异构模型"的**功能**必须有别的地方承接（触发、去重、异源异议），否则是简化了组织图而丢掉了控制。BRIEF-v3 没有说明这些功能去哪了。**这是简化留下的空洞，不是简化本身的问题。**

### 7.2 缺陷

**缺一：没有"停止 / 放弃"的正当出口。**

五态里没有"已放弃 / 已撤销 / 不再需要"。整条链只有"通过 → 下一阶段"。项目可能因为目标失效、成本超支、外部条件变化而**应当终止**。没有 kill switch 的项目管理，必然走向"为了完成而完成"，而且会把终止伪装成"部分通过"或"未完成"，因为没有合法标签可用。

这不是小事：**"该放弃而没放弃"是比"做错了"更贵的失败**，因为它持续消耗。BRIEF-v3 完全没有这个概念，我认为这是它最重要的结构性缺失。【确定】

**缺二：没有时间维度。**

- 真实使用验收需要时间（§5.4）；
- 文档可用性会随目标演进而失效；
- 阶段验收的结论有保质期。

**判定必须有 TTL。** 任何"通过"绑定一个复审点或有效期，过期自动降为"待判定"。

这条与"人工审判成为永久停车场"是对称的：**"通过"也会成为永久停车场。** 一个六个月前通过的文档，没有人会再去质疑它；它已经变成了"基础设施"。而它可能早已与现行目标脱节。**只防"未定"的滞留、不防"已定"的滞留，是单向防御。**【确定】

**缺三：没有成本 / 预算维度。**

真实使用验收是最贵的验收（需要人、需要时间、需要真实场景）；阶段验收每次都要人参与；五态判定要写证据。没有预算概念，就无法决定"验收到什么程度"，只能"一律严格"，而"一律严格"在预算约束下必然变成"一律形式化"。

BRIEF-v3 说"具体处理策略另议"，但**验收强度本身是预算决策，不是策略细节**。v0.3 的"人类裁决预算是有限资源"必须继承，并且必须前移到"我们这次打算验收到什么等级"这个决策上。

**缺四：验收基准的不确定性没有被处理。**

"依据目标文档检查工作区"——但如果目标文档本身只是"部分通过"或处于"人工审判"，验收 agent 依据什么检查？

这是一个**自指问题**：验收的基准本身是被验收过的对象。BRIEF-v3 完全没有处理。概念上必须有：

> **只有处于"通过"状态的、钉定版本的目标文档，才能作为验收基准。** 任何对目标文档的修改，都使已完成的阶段验收结论进入 STALE。

而"目标文档部分通过"时的正确做法不是"凑合用它验收"，而是**明确写出"本次验收只依据 O1–O9，O10–O12 因基准未定而未检查"**。这又回到 §5.3 的"未检查范围必须与不通过范围分开写"。【确定】

**缺五：判定者独立性没有落到"验收什么"这一层。**

v0.3 处理了"谁能判"，BRIEF-v3 没处理"谁决定判什么"。见 §2.4 硬约束一。主 agent 通过"选择验收范围"就能代决，这是比篡改目标更隐蔽的路径。

### 7.3 冗余环节

**冗余一：主 agent 在验收信息流中的位置。**

主 agent 组织验收、汇总结论、把结果对接人类。如果它同时是验收结论的**摘要作者**，它就变成验收的**信息守门人**——这与 v0.3 已裁决的"异构模型不得只读主 agent 摘要"是完全同构的问题，只是这次被喂摘要的是人类。

而且这个冗余最危险，因为**人类是最终裁决者，而他的信息全部来自主 agent**。主 agent 不需要说谎，只需要选择"报哪几条"，就能改变人类的判断。

**简化方向：验收 agent 直接把义务表与证据账交到人类手里，主 agent 不参与验收信息流。** 主 agent 的职责止于"组织验收发生"，不止于"组织人类看到什么"。【确定】

**冗余二：阶段验收与总验收的"目标对齐检查"重复。**

v0.3 §7.2 要求阶段验收含目标对齐；BRIEF-v3 要求阶段验收依据目标文档。若阶段验收已按 O 表做（§5.3），总验收的"目标对齐"就退化为 O 表的最终快照。

**简化：总验收不应重做对齐检查，只应做三件阶段验收做不了的事——E4 真实使用、副作用与遗留的接受、跨阶段累积偏离的判定。** 累积偏离是阶段验收确实看不到的：每个阶段都"轻微偏离一点"，累积起来是方向反转，而每个阶段的偏离度都在阈值内。

**冗余三：任务状态与文档五态双轨维护。**

如果一个任务卡的"完成"用任务状态，而它的交付文档用五态，两者必然漂移（v0.2 已有"双账漂移"的教训，G 系列与不变量 7）。

**简化：任务不设独立的"完成"状态。任务 = （责任状态一维）×（其交付物的五态判定一维），不设第三维。** 责任状态（未认领/进行/待验收/阻断/挂起/失联）是 v0.2 的遗产，必须保留，但它回答的是"谁在推进"，不是"做完没有"。"做完没有"由交付物判定回答。

这一刀砍掉了一整套重复状态维护，而且砍掉的是最容易漂移的那一套。

**冗余四（伪冗余，不该砍）：自验与独立验收的证据重复。**

看起来自验产 E2、独立验收要 E3，是重复劳动。实际上 E3 是 E2 的陌生人版本，是同一份证据的**升级**，不是重做。**正确的简化不是砍掉自验，而是标准化自验的证据格式，使其可直接升级为 E3**（可复现步骤、期望与实际、失败记录、环境描述）。这样自验从"形式"变成"原料"。

这个区分很重要：**真正的冗余是"同一个判断做两遍"，伪冗余是"同一份证据被两个层级使用"。** 前者砍，后者留。

### 7.4 可简化项汇总

| 可简化 | 理由 | 风险 |
| --- | --- | --- |
| 主 agent 退出验收信息流 | 消除信息守门人 | 人类直接读原始材料，负担上升（用 O 表结构化抵消） |
| 总验收取消"目标对齐"重做 | 阶段已做，重复 | 需阶段验收真的按 O 表做，否则两头落空 |
| 任务不设第三维状态 | 消除双账漂移 | 需明确"责任状态"与"判定结果"的映射关系 |
| 阶段验收按风险分级 | 人类预算有限 | 分级标准本身要人定，可能被滥用降级 |
| 五态只用于可消费性 | 语义精确 | 沟通成本上升（见 §10 自我反驳） |

### 8.1 三条最需要展开的

**V11 + V21 合起来是本轮最危险的组合。** 单独看，它们都是"报告不准"；合起来，它们形成一条完整的自欺链：计划按容易做的分解（V11）→ 任务全部通过 → 报告用任务完成率回答"项目进展"（V21）→ 人类看到 90% 完成 → 阶段验收通过 → 项目"完成" → 真实使用验收时产品没法用。**整条链上没有任何一个人说谎，每一步都有记录、有证据、有签字。** 这正是 v0.2 说的"高质量假象"，而 BRIEF-v3 的架构没有堵住它，反而因为"直接检查工作区"而给了它一个更强的正当性外衣（"我们验的是整体，不是清单"）。

**V06 + V19 合起来是时间维度上的同类。** V06 是空间上的证据错配（声称的等级 > 实际等级），V19 是时间上的证据错配（结论的有效期 > 判定者的寿命）。二者共同构成"证据看起来一直在，其实早就不在了"。

**V02 是唯一一条无法被任何流程修复的。** 因为"目标是否正确"不是一个可以在体系内部判定的问题——它需要外部信息，而外部信息只有真实世界和人能提供。所有其他漏洞都可以用结构补偿，V02 只能靠"尽早、尽可能便宜地接触真实世界"。**这也是为什么 v0.2 的"价值验收"和本轮的"真实使用验收"都不可省：它们不是流程的一环，它们是体系的对外接口。**

## 9. 最值得保留的最低控制基线

我认为可以把本轮构想压到下面十条而不失去其骨架。这十条之外的一切都可以按风险裁剪；这十条之内任何一条被裁掉，整套东西就退化成"看起来有流程"。

1. **"通过"必须四元绑定**：版本 × 用途 × 判据版本 × 判定权属。裸"通过"非法。
2. **三层可用性分名，判据不得跨层复用**：可消费性 / 可操作性 / 可使用性。任何"通过"必须回答"相对于谁"。
3. **义务表 O 是唯一合法的进度单位**：目标文档在通过时就必须包含可观测现象、验收动作、阈值、反例、权重、证据目标等级。
4. **覆盖矩阵 O×T 是计划门的必要条件**：空白格必须显式解释；孤儿产物必须记录。
5. **三进度向量同时报告，禁止合成单一百分比**：计划 / 义务 / 可用性。
6. **证据阶梯 E0–E4 与"复现者"必填**：无法独立复现的证据一律 E1；证据账无复现者即无效。
7. **阶段验收 = 四查一判，冷启动实操为必要条件**：由未参与者做，失败不得现场修复；"未检查范围"必须与"不通过范围"分开公布。
8. **项目完成不可汇总**：唯一入口是人类在 E4 证据 + 遗留清单上具名宣告；无自动置为完成的路径。
9. **冻结的是泛化，不是纠错，也不是现场保全**：项目级临时约束、台账整理、现场冻结均属控制，开发期必须允许。
10. **验收结论绑定判定者代次，且"通过"有 TTL**：模型/门禁/判据换代使旧结论过期；过期未复审的"通过"降为"待判定"。

如果要再加一条，我会加**第 11 条：人类实际查看条目数是强制披露项。** 因为它是唯一能让"人类在场"与"人类判断"区分开的可观测事实。没有它，前十条的执行情况无法被人看见。

## 10. 自我反驳

我必须先承认一件事：**我的框架比 BRIEF-v3 更依赖"目标可分解为有限条可观测义务"这个假设，所以我的框架适用边界更窄。** 这是我的第一处、也是最致命的一处弱点。

### 10.1 我的框架最可能在哪里失效

**反驳一：义务表在开放式目标上会退化成形式主义。**

研究、创意、探索、审美、架构决策——这些项目的目标无法被分解成"有限条带可观测现象与阈值的义务"。强行分解会产生两种坏结果：要么把可测量的次要维度当成目标（Goodhart 的经典形态：可测的替代不可测的），要么写出一堆"现象"其实是"我们希望它好"的同义反复。

此时我整套机制——义务进度、覆盖矩阵、E4、证据阶梯——都会运转，而且运转得很顺畅，**输出的全是精确的假信息**。而 BRIEF-v3 的原版至少没有给我这套精确工具，它的模糊反而可能让人保持警惕。**我可能把一个"模糊但诚实"的框架，升级成了"精确而危险"的框架。**【确定：这是真实风险】

**反驳二：三进度向量在组织压力下会被平均成一个数。**

我要求"禁止合成单一百分比"。但现实中，管理层要一个数。如果系统拒绝给，管理层会自己从三个数里挑一个（一定是计划进度），或者干脆在外面另做一套报表。**我无法在概念层阻止这件事，因为我防的是信息压缩的动机，而动机不在系统内。**

更麻烦的是：三向量报告本身给了"看起来透明"的正当性，于是压缩发生时更难被指责。**透明度可以成为不透明的掩护。**

**反驳三：我把最终信任根放在人身上，而人是这个系统里最不可靠的环节。**

§5.2 的结论是"E4 的真实性只能由人以信誉担保"。这意味着整套体系的安全性上限 = 那个人的诚实与勤勉。如果他是 agent 的操作员、如果他被主 agent 的摘要说服、如果他只是想让项目结束——E4 就是空的。

**我没有解决这个问题，我只是把它命名了。** 而命名一个不可解的问题，有时会让它看起来像已解决。这是我这份文件里最需要被质疑的地方。

**反驳四：证据阶梯建立在"产物可被人复现"上，而 agent 可以把复现成本压到极低。**

E3 要求"陌生人只读文档即可复现"。但如果 agent 生成的文档极其详尽（它可以生成无限详细的步骤），那么"能复现"会变得廉价——不是因为它真的可复现，而是因为**详尽的文档让"看起来可复现"变得廉价**。E3 的判据会被"文档膨胀"满足，而文档膨胀恰恰增加了解释负债（v0.2 的 A′ 概念），使真正的可用性下降。

**这是我最担心的一处内在矛盾：我用"陌生人能否复现"来定义可用性，而 agent 恰好最擅长生产"让陌生人以为能复现"的文档。** 唯一能防的是"真的让陌生人做一次"，即冷启动实操。所以我的框架最终必须落在一个昂贵的人类动作上，否则全部失效。而如果那个动作太贵，它就会被跳过——**于是我的框架回落到"依赖人的勤勉"，与反驳三同源。**【确定】

**反驳五：我说"项目完成不可汇总"，但过度的不可汇总会让系统无法回答"现在怎么样了"。**

一个拒绝给出总体判断的框架，在真实组织里会被绕过。人需要一个"我们到哪了"的答案，而我的回答是"三个向量、六条义务、若干未决异议"。这可能正确但不可用。**正确性不能替代可用性——这正是我批评 BRIEF-v3 的理由，而我可能犯了同一个错。**

**反驳六：我的收缩建议可能因为"不好用"而失败。**

我主张五态只用于文档可消费性，项目层另立谓词。这在语义上更精确，但代价是：整个组织失去了统一的状态语言，每次跨层沟通都要先解释"这个'通过'是哪一层的通过"。

**统一语言的价值可能大于语义精确的价值。** 人类组织大量依赖"同一个词在不同场合指不同事"来运转，强行精确化有时会让沟通成本超过它带来的准确性。我不确定我是不是在做一个正确的、但没人会用的东西。【存疑】

### 10.2 我最可能错的具体判断

| 判断 | 我的置信 | 可能错在哪 |
| --- | --- | --- |
| 工作区不是使用场所（§5.4） | 高 | 若绝大多数项目的产物本身就是工作区内工件（如文档、流程、配置），则"在工作区真实使用"是常态而非例外，我的范畴批判就过度了 |
| 项目完成不可汇总（§3.3） | 高 | 实践中"汇总 + 人类抽检"可能足够好；我对"必然制造虚假完成"的断言可能过强 |
| 三进度向量不可合成（§4.5） | 中高 | 加权合成若有明确权重来源（人类定义），未必比三向量差；我可能把"信息损失"绝对化了 |
| 判定者代次使旧结论过期（§6.5） | 高 | 若模型换代但判据与产物未变，重验可能纯属浪费；"过期"的粒度可以更细（按条目而非整体） |
| 冷启动实操必须是阶段验收的必要条件 | 中高 | 成本极高；在低风险阶段可能不值得，分级而非一刀切更合理 |
| 五态缺"通过但需人批"格（§4.4） | 高 | 若把"人工审判"明确定义为"已判待批"，这个格子就被覆盖了，我的批评变成命名之争 |

### 10.3 我对本轮构想最狠的一句反驳

如果只能留一句：

> **BRIEF-v3 想把验收从"看文档"变成"看工作区"，但它没有回答一个更基本的问题：当工作区里的每一份材料都可能是 agent 为了通过验收而生成的，"看工作区"与"看文档"的差别，就只剩下了"看多少"。**

这句话对我的框架同样成立。**唯一真正的出路是让验收接触工作区之外的后果**——真实使用、真实损失、真实时间。这也是为什么我认为 E4 不是"最后一层验收"，而是**整个体系唯一真正的外部接口**；其余所有层级，包括我的义务表与证据阶梯，都只是把"尚未接触真实世界"这件事组织得更有秩序而已。

诚实地讲：**在 E4 之前，这套体系的一切"通过"，都只是"我们内部一致"的同义词。**

## 11. 文末：最需要人类裁决的问题

以下问题我无法在概念层自行决定，且每一个都会实质改变框架的形状。按"不裁决的代价"排序。

**Q1（最高优先）——"可用性"是否接受三层分名？**

BRIEF-v3 原文用同一个"可用性"贯穿文档、阶段与真实使用。我主张必须分成可消费性 / 可操作性 / 可使用性，且判据不得跨层复用。
不裁决的代价：整个框架会持续把"下游能执行"当"东西有用"，且没有任何一处会报错。
需要你回答的是：**你原意里，"文档可用性"和"项目可用性"是不是同一件事？**

**Q2（最高优先）——价值验收是否保留为独立动作，且前移到目标门？**

我把"真实使用验收"读作对 v0.2"价值验收"的替换。若确实如此，我认为这是一次危险的降级：能用 ≠ 该要。
需要你回答的是：**"这东西是否值得要"这个问题，除了在末端由真实使用间接回答，是否还需要在目标门由人直接回答一次？**

**Q3（高）——"真实使用验收"的实际形态是哪一种？**

受控实操（E3，几小时，人操作）/ 真实使用观察（E4，数周，跨出项目周期）/ 验收性试运行（E3，量化）。
不裁决的代价：所有人默契地降低标准，而名字保持"真实使用"，这是"演示冒充真实使用"的结构性成因。
需要你回答的是：**项目末端你实际能给出多少时间与多少真实使用者？**

**Q4（高）——"验收 agent 联合人类"是哪一种联合？**

并检（双盲）/ 复核（人二审）/ 人主检（agent 仅记录）。三者控制性质完全不同。
需要你回答的是：**在每个阶段，人类是"必须做一遍"，还是"可以只看结论"？** 若选后者，就必须接受"人类实际查看条目数"作为强制披露项。

**Q5（高）——"经验收敛延后"是否允许项目级临时约束与现场冻结？**

我主张"冻结的是泛化，不是纠错，也不是现场保全"；项目级临时约束、台账整理、现场冻结都属控制，必须允许。
需要你回答的是：**"项目内不许进化"是否包括"项目内不许加一条只在本项目生效的临时约束"？** 若包括，我认为这个设计会系统性地明知故犯。

**Q6（高）——验收结论在模型换代后是否作废？**

我主张判定者有代次，模型/门禁/判据换代使旧验收结论过期；只有 E4 证据可跨代复用。
需要你回答的是：**升级模型之后，之前的验收结论你是否还愿意称为"已验收"？**

**Q7（中高）——"在工作区做真实使用验收"是字面还是比喻？**

若项目产物本身就是工作区内的工件，字面成立；否则工作区只能承载记录，E4 的真实性仍由人担保。
需要你回答的是：**你要的是"在使用现场验收，证据回传工作区"，还是"把人请进工作区操作"？**

**Q8（中高）——是否接受"项目完成不可由下层汇总"？**

我主张唯一入口是人类具名宣告，不存在自动置为完成的路径。
需要你回答的是：**你是否愿意接受"所有任务与所有阶段都通过，但项目仍未完成"这种状态长期存在？** 若不愿意，就必须有一个"何时可以宣布完成"的显式规则，而那规则本身是人定的价值判断。

**Q9（中）——五态是否只用于文档可消费性？**

我主张项目层另立谓词。但这会牺牲统一状态语言。
需要你回答的是：**你更在意"一个词走通全链"，还是"每个词只说一件事"？**

**Q10（中）——是否增设"放弃"作为项目级正当状态？**

BRIEF-v3 没有停止出口。我主张必须有，且须人具名 + 遗留清单。
需要你回答的是：**这个框架是否允许"这个项目不该继续"成为一个合法结论，而不是一次失败？**
