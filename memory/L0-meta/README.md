# L0 元知识（跨项目）

## 放什么

- 跨项目稳定的原则、模式、反模式；
- 判断准则与决策启发式；
- 经过反例检验的"什么时候不适用"。

## 不放什么

- 只在一个项目成立的细节（→ L1）；
- 具体操作步骤（→ 技能卡）；
- 未经验证的直觉（→ L2 观察）。

## 条目模板

```markdown
### MK-000 标题
- 类型：原则 / 模式 / 反模式 / 判断准则
- 主张：一句话
- 适用条件：
- 反例 / 失效条件：
- 证据：来自哪些项目、哪些错误条目
- 置信度：高 / 中 / 低
- 复审日期：
- 所有者：
- 状态：candidate / active / superseded / archived
```

## 当前候选条目（尚未批准，仅作示范）

### MK-001 验收标准必须先于执行写定
- 类型：原则
- 主张：验收标准在派发前写定；执行中修改标准必须走变更并留痕。
- 适用条件：有明确交付物的工程任务。
- 反例：探索型任务的目标本身在演化，标准只能随假设更新，但每次更新仍需留痕。
- 置信度：中（待跨项目验证）
- 状态：candidate

### MK-002 单样本错误不得晋升为规则
- 类型：原则
- 主张：一次错误只能作为观察；至少同根因复现两次，才考虑写成项目级检查项。
- 适用条件：所有错误沉淀场景。
- 反例：造成不可逆损失的错误，可立即写成"禁止项"，但仍需标注为紧急规则并在复审时重新评估。
- 置信度：中
- 状态：candidate

### MK-003 验收者不得与被验收者共享同一上下文
- 类型：原则
- 主张：验收必须由独立入口完成；至少做到"只读工件、不读执行过程"。
- 适用条件：中高风险任务。
- 反例：极低风险、可自动判定的任务，可由同一执行者自检，但需标注"自检"而非"验收"。
- 置信度：中
- 状态：candidate
